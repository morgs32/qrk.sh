## What causes the release conflict

All Brick kinds currently share a versioned `brick` model whose `moduleId` is an enum. The candidate Brick V7 adds `text`. The owner and actor bind that model, and SystemSpec validation requires a contract's models to match the owning release's bindings. A current command cannot simply keep the old Brick V6 binding while its owner selects V7. Brick V7 (former V21 draft), candidate owner (former V21 draft), candidate actor (former V21 draft), [SystemSpec model validation](../../../zerospin/packages/core/src/system/SystemSpecSchema.ts).

QRK's Add factory explicitly types its library as `typeof candidateLibrary` and its callback model as earlier Brick versions; its callback also supplies a manually correlated `MODULE` generic. Update's factories similarly name the earlier catalog and Brick models. The new Add V14 and Update V15 select Brick V7 and the V21 catalog, so these existing callback parameter types do not accept the new inputs. The backend test TypeScript check reports three callback assignment errors. [Add factory](../../apps/zerospin/src/aggregates/user/contracts/wall/AddBrickContractV11.ts), [Update factory](../../apps/zerospin/src/aggregates/user/contracts/brick/UpdateBrickV12.ts), candidate Add (former V21 draft), candidate Update (former V21 draft), [catalogs](../../apps/bricks/src/modules/candidateLibrary.ts).

Zerospin's upgrade API supplies overridden callback input types from the patched payload, models, and operations, and an omitted program inherits the previous callback. Inline callbacks can therefore receive the new release's context without the particular QRK factory signature. Construction inherits the old callback without proving it accepts the patched inputs; omitting a callback to silence a type error would not establish safety. That is a potential SDK soundness issue to investigate separately, not proof that a new capability is required. The observed error is at the QRK factory boundary; it does **not** by itself establish that Zerospin needs catalog injection or a different SDK API. [Ordinary upgrade signature](../../../zerospin/packages/core/src/contracts/make/upgradeAggregateContractRelease.ts), [callback inheritance](../../../zerospin/packages/core/src/contracts/make/constructContractRelease.ts).

TypeScript infers a function parameter from a suitable surrounding callback type; the current `setPlacementSpec` draft is an in-repository example that passes the backend typecheck. This does not establish that the complete Add and Update programs will compile until those callbacks are actually authored and checked. [TypeScript contextual typing](https://www.typescriptlang.org/docs/handbook/type-inference#contextual-typing), draft command (former V21 draft).

The existing Add and Update commands are shared application behavior: Add checks ownership, placement and Wall fit and creates the Brick and Placements; Update validates state, advances the state revision and supersedes relevant pending generations. The Wall editor dispatches these general commands. Dedicated Text commands can directly select Text's state schema, but other Brick commands still read the evolved shared Brick model, and the common placement work would need to remain shared or be repeated. Per-kind models would be a broader, unverified redesign. [Add program](../../apps/zerospin/src/aggregates/user/contracts/wall/AddBrickContractV11.ts), [Update program](../../apps/zerospin/src/aggregates/user/contracts/brick/UpdateBrickV12.ts), [Wall editor](../../apps/app/components/WallEditor/WallEditor.tsx).

## Replay and historical behavior

A fresh parallel release evaluates retained history through its own registered release; reconstruction with retained release output replays recorded operations instead of re-evaluating the program. Source payloads and edge adapters must remain available, and a valid newer payload the old release cannot represent may be explicitly refused on the down edge. The focused local adapter test covers the V13 to V14 Add payload and refusal of Text by the prior Add and Update releases; it does not establish live replay or publication progress. [Replay implementation](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts), [payload adaptation](../../../zerospin/packages/core/src/contracts/decodeAndAdaptPayload/adaptPayload/adaptPayload.ts), [local adapter test](../../apps/zerospin/test/textRelease.spec.ts).

The historical Add factory closes over its supplied candidate catalog, but its row-sharing and minimum-width checks also read the global `backendLibrary`. The older generation continuation similarly imports that global library. Consequently, keeping historical catalog keys alone is not proof that fresh evaluation of historical callbacks is frozen to their original module definitions. Avoid changing old callback behavior implicitly; verify this dependency separately for any proposed change. Previously retained operations and a fresh evaluation have different execution paths. [Historical Add](../../apps/zerospin/src/aggregates/user/contracts/wall/AddBrickContractV11.ts), [historical generation continuation](../../apps/zerospin/src/aggregates/user/contracts/brick/GenerateBrickSpecExternalV2.ts), [backend library](../../apps/bricks/src/modules/backendLibrary.ts).

## Placement spec boundary

The generic metadata-derived schema accepts either a literal or `$state` reference for each component prop. Its document schema permits more than one element; generic element fields also permit visibility, repeat and other behavior. For Text, that means a valid-looking document can use dynamic typography, provide literal or differently bound content, have more elements, or hide/repeat the block. The draft editor expects a root `TextBlock` with literal `fontFamily` and `fontSizePx`; the default Text spec binds `content` to `/content`. A mismatched spec can fail to open or make published content diverge from what is edited. [Component spec schema](../../apps/bricks/src/definition/makeComponentSpecSchema.ts), [document schema](../../apps/bricks/src/definition/makeModuleSpecDocumentSchema.ts), [stored spec schema](../../apps/bricks/src/definition/placementSpecSchema.ts), [Text definition](../../apps/bricks/src/modules/text/definition/textV1.ts), [Text editor](../../apps/bricks/src/modules/text/react/TextEditor.tsx), [Text renderer](../../apps/bricks/src/modules/text/react/TextBlock.tsx).

There are three relevant checks: the Bricks generation worker checks provider output, the aggregate's generation continuation validates again before saving, and the proposed manual Placement-spec command validates the submitted spec. The V10 continuation currently inherits its program from earlier releases. Changing the old continuation directly would also change a historical callback; a new-release override and release-specific module declarations need consideration. [Bricks generation worker](../../apps/bricks/worker/generateSpec.ts), [generation continuation](../../apps/zerospin/src/aggregates/user/contracts/brick/GenerateBrickSpecExternalV2.ts), candidate continuation (former V21 draft), candidate manual command (former V21 draft).

## Candidate directions

1. **Concrete callbacks for the new release.** Write the Add and Update guard/program against their V21 declaration context and the V21 catalog, preserving existing contracts and historical factories. This uses current SDK capabilities and preserves required catalog keys, but repeats substantial behavior that must stay consistent on future changes. It still requires full replay and behavior verification. This is a bounded option, not a tested implementation.
2. **Redesign shared QRK authoring.** Investigate whether shared domain operations can express placement and state updates without manually coupling callback types to model versions. Any abstraction must retain exact model/operation types, correct release catalogs, and historical behavior; a string-keyed record or optional lookup would weaken required-catalog guarantees. No concrete design has yet been validated.
3. **Change Zerospin's API.** A release-bound typed capability could be explored, but its identity, lifetime, replay behavior and application ownership are unresolved. Source inspection has not shown it is required, so do not assume an SDK change solves the issue.
4. **Separate commands per Brick kind.** This narrows each command's content validation but does not alone remove shared-model evolution or common Wall behavior. Separate models would require a larger investigation, including queries, layout, publication and replay.

For specs, a possible design is a module-owned complete Placement-spec schema, analogous to each module's complete state schema. Text's schema would require one root TextBlock, its content binding and literal typography, and exclude unsupported document behavior. Generic save and generation paths would invoke the selected module's schema, rather than know about Text. This adds a shared module contract and needs an explicit decision about exact shape and use sites. Historical continuations must retain their behavior; any new continuation validation must be bound to the new release. Ensure restored existing content and every actual write path have an appropriate validation boundary before relying on the editor's assumptions. This is a proposal, not implemented behavior.
