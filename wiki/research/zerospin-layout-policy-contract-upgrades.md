# Layout policy compatibility through contract upgrades

Researched 2026-11-02 against QRK's installed `@zerospin/core` **38.2.2** and the owning sibling Zerospin source. This is research for Stack insertion and no-overflow validation, not an approved implementation design. [Installed version](../../apps/zerospin/node_modules/@zerospin/core/package.json#L3).

## Findings

1. **A fresh parallel Aggregate release evaluates historical commands under its own selected contract.** It resolves the execution contract from that release, adapts the submitted payload to the selected version, and prepares the invocation. Consequently, a newly added fit guard can refuse an addition that an older release accepted. This differs from recovery with the same release's retained evaluated output: that branch restores its output rather than reevaluating the program. Missing original-release output is an error. [Execution selection](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/utils/resolveExecutionContract.ts#L14), [adapted invocation](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/utils/resolveAggregateExecution.ts#L98), [restore/evaluate branches](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts#L40), [missing original output](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L46).

2. **Ordinary contract upgrades can preserve legacy payload semantics.** An explicit `up` can add a policy such as `legacy` to old input. Adaptation walks the version edges and validates the decoded result against the destination's decoded schema. That allows a new program to retain the older behavior for adapted input; an adapter does not automatically preserve the predecessor's program behavior. [Adapter execution and destination validation](../../../zerospin/packages/core/src/contracts/decodeAndAdaptPayload/adaptPayload/adaptPayload.ts#L75), [selected execution contract](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/utils/resolveExecutionContract.ts#L14).

3. **A current Actor session cannot submit an arbitrary older contract version.** Session selection requires the exact version exposed by that Actor, and fresh Aggregate command admission repeats the exact-version check. This corrects the earlier concern that a caller using the current session could simply select an old version from the upgrade lineage. Historical decoding support is separate from fresh-command support. [Session contract selection](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/authorizeSession/selectAggregateLockMembers.ts#L65), [fresh admission](../../../zerospin/packages/system-worker/src/AggregateChain/admitAggregateCommands/validateNewAggregateCommand.ts#L52).

4. **An ordinary `legacy` field accepted by the new payload schema is also available to fresh callers of that version.** An upgrade adapter can supply it, but does not make it an adapter-only field. Contract callbacks receive the payload, claims, database, failures, and owner scope; their input does not contain the submitted contract version. [Submitted payload validation](../../../zerospin/packages/system-worker/src/AggregateChain/admitAggregateCommands/validateNewAggregateCommand.ts#L71), [callback input](../../../zerospin/packages/core/src/contracts/types.ts#L170).

5. **A strict-wire/broader-decoded codec does not preserve an adapter-only marker through the current preparation path.** Although adaptation validates `Schema.toType`, `prepareAggregateInvocation` subsequently calls `validateCurrentPayload`. For JSON fields, preparation encodes the adapted value through the full codec and decodes the payload again. [Decoded adaptation](../../../zerospin/packages/core/src/contracts/decodeAndAdaptPayload/adaptPayload/adaptPayload.ts#L97), [invocation preparation](../../../zerospin/packages/core/src/contracts/prepare/prepareAggregateInvocation.ts#L55), [JSON encode/decode](../../../zerospin/packages/core/src/contracts/validatePayload.ts#L98).

   A read-only in-memory probe against installed 38.2.2 confirmed the consequence: V1 `{}` upgraded to V2 `{ policy: "legacy" }`, using a V2 codec whose wire value permits only `fit` and whose decoded value permits `fit | legacy`. Adaptation returned `legacy`. A passthrough encoder then failed preparation with `encode-command-json-payload-field-failed` and `Expected "fit"`; an encoder mapping `legacy` to `fit` prepared successfully but lost the legacy distinction. No fixture or source files were written by this probe.

6. **Retaining old owner releases leaves a separate admission route unless application policy retires it.** Session authorization resolves the requested Aggregate version from the registry, and fresh admission selects the command's addressed release. The inspected selection paths do not require the canonical release. Updating the current Actor therefore does not, by itself, retire previously supported owner/Actor sessions. [Session release resolution](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/authorizeSession/authorizeSession.ts#L64), [command release resolution](../../../zerospin/packages/system-worker/src/AggregateChain/admitAggregateCommands/validateNewAggregateCommand.ts#L18).

## Proposed Page-level policy — unresolved

QRK's current Page model has no layout policy, and `createPageV2` changes only its Wall binding. A persisted Page policy could be read by layout contracts instead of exposing a per-edit compatibility switch. Its field, initialization, and transition behavior have not been approved. [Page model](../../apps/zerospin/src/aggregates/user/models/page/PageV1.ts#L9), [current creation upgrade](../../apps/zerospin/src/aggregates/user/contracts/createPage/CreatePageV2.ts#L5).

A static `legacy` value would govern both replayed historical edits and future edits to that same Page. It would not alone distinguish “preserve old accepted overflow” from “reject new edits that worsen overflow.” Whether legacy Pages stay permissive or transition to enforced fit remains a product decision; this note does not settle it. This follows from the proposed persisted-state check and the existing callback inputs, rather than from an implemented Page policy. [Callback input](../../../zerospin/packages/core/src/contracts/types.ts#L170).

## Conclusion and verification limits

Contract upgrades already provide historical payload adaptation. They do not currently establish an adapter-only policy through invocation preparation. Exposing original-version context was an initial suggestion, not an established necessary or sufficient fix. No SDK change, Page policy, model migration, storage reset, dependency update, or feature implementation is authorized by this research.

The subsequent design decision supersedes the compatibility requirement for this feature: the user authorized wiping **local development and deployed QRK Zerospin data** at its cutover. [Plan 050](../plans/050-plan-stack-insertion-and-fit.md) therefore uses strict fit validation with fresh storage, without a Page legacy flag or SDK change. This records authorization and intended work; no reset has been executed by the research.

Evidence consists of source inspection and the bounded codec probe above. Existing framework tests were read, not run; this is not browser, Durable Object delivery, admission integration, or production verification. Installed core files checked during the investigation matched the inspected sibling implementations. Sibling Intent discovery was unavailable; QRK's installed Intent discovery and evolution guidance were used without downloading a replacement.
