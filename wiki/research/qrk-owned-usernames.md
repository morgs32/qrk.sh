The existing User model declares a unique username field, but that model is inside each separately identified User aggregate, so this declaration alone does not enforce uniqueness across accounts. ## Shared service and availability

A Zerospin Service owns one shared data set across users; individual User aggregates instead have separate owner boundaries. A service actor authenticates the requester and exposes selected rows; writes must authorize against verified claims and canonical state. A model can declare unique indexes, and a create/update command can recheck the desired normalized username inside its authoritative savepoint. [Owner distinctions](../../../zerospin/fragment/content/handbook/aggregates-and-services.md), [actor authorization](../../../zerospin/packages/sdk/skills/zerospin-authorize-actors/SKILL.md), [unique-index example](../../../zerospin/examples/shopping/src/zerospin/aggregates/user/models/cartItem/CartItemV1.ts).

A debounce is UI behavior: cancel or ignore an older answer when the input changes. The availability read is advisory. Two users can both see available before either attempts to save; the Service must decide the winner during canonical command execution and give the loser a useful refusal. Rehearsal and local projection cannot reserve the name. [Session validation](../../../zerospin/fragment/content/guides/write-commands.md), [completion boundaries](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md).

Example: Alice and Bob each see `morgan` as available. Alice's claim commits first. Bob's later authoritative command must refuse the name even if his earlier check and local optimistic stage succeeded; his UI then shows that it was taken. The check improves feedback, while the Service's single shared write boundary decides ownership.

There are two existing reading boundaries to evaluate rather than assuming a named service query exists:

- An authenticated Service session exposes only its Actor's selected rows into a local reactive SQLite projection; a `useLiveQuery` key must change with a changing input. An unfiltered catalog example selects every row. If availability uses this approach, decide deliberately whether exposing/replicating the entire username namespace is appropriate; a missing row from an owner-only selection does not prove global availability, and a local projection can be stale or optimistic. [Catalog actor](../../../zerospin/examples/shopping/src/zerospin/services/marketplace/actors/catalogActorV1.ts), [query-data guide](../../../zerospin/fragment/content/guides/query-data.md), [admission and visibility](../../../zerospin/packages/sdk/skills/zerospin-authorize-actors/references/admission-and-visibility.md).
- A trusted server can use a typed `SystemApi.executeServiceQuery` with a narrow filter and projection, keeping the administrative secret server-side. That read returns current materialized data for the selected release, does not create a command or reserve anything, and must not be exposed as an unrestricted administrative API. The existing published-page reader already uses the corresponding aggregate API; an authenticated endpoint for availability would still need an explicit contract and security decision. [System API read](../../../zerospin/fragment/content/reference/sdk.md), [existing QRK reader](../../apps/web/library/readPublishedPage.ts).

## Staging is not confirmation

`stageServiceSessionCommand` returns synchronously after local staging; success is the local program result, not proof of server admission or successful execution. The local session query can immediately show the optimistic new username. Connectivity loss or canonical rejection leaves a different outcome than the local return. Background delivery and reconciliation belong to the session; do not automatically submit a duplicate because delivery is uncertain. [Session phases](../../../zerospin/fragment/content/handbook/sessions-and-synchronization.md), [submission reference](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md).

The browser retains a session command row with `sessionIndex`, nullable `serviceIndex`, and nullable public `failure`; node-view installation records a matching resolution. A null failure by itself is **not** confirmation, and the complete canonical outcome remains in Chain history. The SDK guidance recommends domain-state observation and identifies retained command rows as diagnostic/correlation evidence. Investigate the supported public session API and the precise behavior for rejected admissions, reconnects, other tabs and recovered submissions before designing a user-facing confirmed-state control; do not assume a general Promise waiter exists or implement a consumer workaround for an SDK gap. [Service session table](../../../zerospin/packages/core/src/serviceSession/serviceSessionRepoTables.ts), [view installation](../../../zerospin/packages/core/src/serviceSession/installServiceNodeView.ts), [synchronization semantics](../../../zerospin/fragment/content/handbook/sessions-and-synchronization.md), [completion guidance](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md).

For the requested UI behavior, the Publish action must remain unavailable while the relevant username save is pending or refused, including offline and reconnect situations. A plain live-query value is insufficient evidence that the requested command completed authoritatively. Whether to use supported correlated session resolution, a narrowly scoped authoritative server read, or a framework capability needs design and API verification; an authoritative read of an existing matching name does not by itself prove a particular newer save succeeded, especially for repeated or concurrent edits.

A server-only current-state query could establish that a specific normalized username is currently mapped to the signed-in user: authenticate the caller, derive their Clerk subject from the verified credential, query the canonical Service release for both values, and expose only the minimal answer. The server secret stays server-side. This is evidence of the state at that read, not evidence of a particular command's outcome, and a later rename can invalidate it. Such an endpoint needs a deliberate authentication, caching, error and offline contract; it is not present in QRK today. [Administrative read semantics](../../../zerospin/fragment/content/reference/sdk.md).

## Is a continuation required?

Not merely because a creator saves a username and waits before clicking Publish: a direct Service actor command can validate and write a username in its own owner transaction. A provider request/recorded continuation is a separate mechanism. A cross-owner recorded command is delivered separately; its destination result does not rewrite the source command's success. If publishing must be authoritatively prohibited for every client until a username exists, UI gating alone does not enforce it: the current `publishSite` runs in the User aggregate, while the username would belong to the Service. An aggregate session has no general synchronous service-read capability, and a cross-owner read/commit is not automatically atomic. If required, choose and justify an authoritative cross-owner design; do not assume a continuation solves ownership, freshness or ordering automatically. [Shared service and owner boundaries](../../../zerospin/fragment/content/handbook/aggregates-and-services.md), [external-work guidance](../../../zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md), [publish guard](../../apps/zerospin/src/fresh/contracts/PublishSiteV1.ts).

## Decisions to settle before implementation

1. Normalize and validate usernames consistently, including case, reserved infrastructure labels and DNS length. The Site slug plus hyphen plus username must fit a single DNS label. For a rename, decide what happens if existing Site slugs would exceed that limit.
2. Decide whether a username can be reclaimed immediately after a rename, reserved, or redirected. Published URLs and sharing/QR codes change; releasing an old name could route old links to a different account. Decide if already-published Sites stay visible at the new hostname and how long old links should work.
3. Choose the owner and public exposure for the username-to-account mapping and who may query it. Enforce account ownership and global uniqueness on canonical writes, not just in the input field. Choose the behavior for a first-time user, offline mode, conflict, failed delivery, and re-entry.
4. Decide whether the publishing restriction is strictly a UI rule or an authoritative system invariant across clients. Resolve how to establish confirmed username state across Service and aggregate boundaries before implementing it.
5. The current Web handoff and App's `$username` route assume an existing Clerk username. Decide the signed-in route before choosing a name, and navigation/redirect behavior after changing it. Determine handling of current Clerk accounts and existing QRK data; a prior local database wipe did not delete Clerk accounts and does not by itself authorize further resets.
