# Aggregate query freshness and QRK publication

Researched 2026-11-16 against QRK's working tree and Zerospin commit `4221aa282a5aa449af5c9a8dc7310a7a817b951d`. The QRK Web reader's direct User V4 binding is an **uncommitted change** at the time of this investigation. This note describes the existing query behavior and the proposed boundary; it does not approve or implement a read barrier.

## The question

Plan 091 requires a V4 public read after a successful V4 unpublish commit not to serve the Site; the user accepts that V4 can lag commands from other releases. User V1 remains canonical while User V4 is registered; the App addresses V4 and the Web reader queries V4. When does a committed unpublish reach that Web read? [Plan 091](../archive/plans/091-plan-domain-assignment-and-command-continuations.md#agreed-behavior), [registry](../../apps/zerospin/src/system.ts#L12), [App session](../../apps/app/zerospin/userSessionDefinition.ts#L38), [Web reader](../../apps/web/library/readPublishedPage.ts#L60).

## What a query reads today

The System API resolves the requested registered `aggregateVersion` to its own `AggregateVersionRepo`. Its normal query reads that release's current committed SQLite rows under that repo's execution permit. It does **not** request Chain catch-up for every read. When a repo activates, it first catches up to a captured finalized prefix; subsequent finalized commands are also delivered by background fanout. That activation behavior is not a per-query freshness guarantee. [SystemWorker dispatch](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/executeAggregateQuery/executeAggregateQuery.ts#L25-L42), [repo activation and query](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateVersionRepo/AggregateVersionRepo.ts#L263-L269), [query permit](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateVersionRepo/executeAggregateQuery/executeAggregateQuery.ts#L40-L54), [Chain fanout](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateChain/AggregateChain.ts#L153-L160).

### Same-release case: V4 unpublish, then V4 read

1. The current App's Unpublish button stages a command against its V4 session. Staging success commits optimistic local work; it is **not** proof that server execution committed. [Button](../../apps/app/app/%5Busername%5D/site/%5BsiteId%5D/page/%5BpageId%5D/SiteSettings/SiteSettings.tsx#L585-L598), [staging boundary](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/sdk/skills/zerospin-submit-commands/SKILL.md#L31-L44).
2. Once the admitted command actually commits its successful original execution in the **V4 AggregateVersionRepo**, V4's Site row has `isPublished: false`. A later V4 query uses the same repo permit as that execution and reads the committed V4 state. This same-release case does not require waiting for another release's replay. [Original execution permit](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommand.ts#L67-L97), [unpublish operation](../../apps/zerospin/src/fresh/contracts/UnpublishSiteV1.ts#L63-L69), [V2 inherits V1](../../apps/zerospin/src/fresh/contracts/UnpublishSiteV2.ts#L6-L13).

### Cross-release case: V1 unpublish, then V4 read

1. Suppose a Site is published in both V1 and V4, and V4's repo is already active. A still-registered V1 session admits an unpublish command; its original execution commits the V1 Site row as unpublished. The V1 Actor declares `unpublishSite`. [V1 Actor](../../apps/zerospin/src/fresh/userActorV1.ts#L164-L178), [original delivery](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateChain/AggregateChain.ts#L572-L603).
2. The original repo's materialization commits before the Chain has necessarily retained that original outcome and advanced `finalizedThroughIndex`. Only the finalized prefix is available to the replay reader; after outcome retention, fanout delivers the admitted command to other releases. [Original materialization transaction](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts#L16-L17), [Chain outcome retention](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateChain/recordOriginalCommandOutcomeTx.ts#L107-L117), [finalized replay boundary](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateChain/readReplayPage.ts#L13-L30), [fanout wake](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateChain/AggregateChain.ts#L290-L307).
3. If Web queries the already-active V4 repo before V4 materializes that command, V4 may still report the Site as published. Its two Web reads recheck the Site, Page and snapshot pointer **within V4**; both can agree on the same stale V4 state. Once V4 successfully applies unpublish, later V4 reads see the updated state. [Web's two V4 reads](../../apps/web/library/readPublishedPage.ts#L72-L115), [V4 replay permit](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L63-L72).

### Controlled reproduction

An existing disposable Workerd fixture drove a real `AggregateChain` and both QRK User releases. It published a V1 Site, brought V4 through that history, deliberately held V4 fanout, and then admitted and finalized V1 `unpublishSite` at index 5. The V1 Site row was unpublished, while the actual V4 `executeAggregateQuery` still returned `isPublished: 1`. The focused run passed: one test passed and six were skipped. [Fixture](/private/tmp/qrk-replay-check/replay.workerd.spec.ts#L11).

This establishes the stale **cross-release VersionRepo query** under controlled delayed delivery. The Site had no assigned hostname, so it is not a full public Web request test. The fixture released the held delivery during cleanup but did not assert V4's later catch-up. It used the framework worktree at `a9ed08a29ee78d76b7d470f6aab2c8b35e2341a4`; the three inspected Chain, VersionRepo, and query files are unchanged between that commit and `4221aa282a5aa449af5c9a8dc7310a7a817b951d`.

Canonical selection does not choose the release on which the admitted command originally executes or the explicit release queried by Web. This cross-release case is possible because the releases remain registered, not because V4 is noncanonical. A canonical repo can also be behind another addressed release. [Parallel-model semantics](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/sdk/skills/zerospin-parallel-models/SKILL.md#L25-L37).

## What the proposed barrier would buy

An optional design would capture the AggregateChain's already-admitted tip, progress original commands through that fixed index, replay the resulting finalized prefix into the requested release, then read that release. Existing `executeCommandsThrough` captures `admittedThroughIndex` and drains the original outbox; the existing catch-up routine captures a finalized replay tip. Neither step is currently part of every query. Cross-owner waits must not hold the VersionRepo's execution permit needed by materialization. [Original execution through an admitted index](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateChain/executeCommandsThrough/executeCommandsThrough.ts#L27-L46), [bounded replay catch-up](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/makeFanoutSubscriber/runFanoutCatchup.ts#L42-L70), [existing result wait](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateVersionRepo/awaitCommandResult/awaitCommandResult.ts#L25-L42).

The barrier is bounded to commands admitted before its capture, not offline browser work or later admissions. A query could now drive original execution, wait, or fail because of pending work. Catching up only the *already-finalized* prefix is narrower and can miss the window between another release's materialization commit and Chain outcome retention.

Even reaching the captured index is not proof of equal business state: a first evaluation in another release runs that release's contracts and can produce a different outcome; retained reconstruction restores that release's retained output. A concrete V1-to-V4 unpublish in the disposable Workerd fixture succeeded in both releases and changed the V4 Site to unpublished, but that single materialization case does not establish all histories, concurrent reads, durable Chain delivery, or browser synchronization. [Replay behavior](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L14-L15), [fresh evaluation versus retained output](https://github.com/morgs32/zerospin/blob/4221aa282a5aa449af5c9a8dc7310a7a817b951d/packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts#L37-L54), [fixture](/private/tmp/qrk-replay-check/replay.workerd.spec.ts).

## Decision

The user accepted cross-release eventual consistency: QRK does not require a global read barrier to make V4 immediately reflect commands committed by other registered releases. Verify successfully committed **V4-origin** unpublication through the real boundary; the existing same-repo serialization addresses that ordering. Keep the final V4 pointer and publication recheck for changes during a public read.
