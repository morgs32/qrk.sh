# Dashboard one-click site creation design

**Date:** 2026-07-17
**Status:** Approved for planning

## Problem Statement

The authenticated dashboard renders a “Create site” button that performs no action. The current `createSite` and `createPage` contracts also require the browser to provide resource IDs and authored text values even though a new workspace should begin without authored metadata. Navigating through bare `/site/:siteId` compounds the problem by rendering page-scoped controls before a real Page ID exists.

## Solution

Make Site and Page metadata nullable with null defaults, move both resource IDs into their contracts, and stage one Site followed by one initial Page through the existing Zerospin owner session. Navigate only after both local commands succeed, using their generated IDs directly. Local staging never produces pending UI; an encoded staging failure remains on the dashboard as an inline error.

## User Stories

1. As a signed-in owner, I want one click to create a site without completing a form.
2. As a signed-in owner, I want the initial Page created with the Site so that the workspace URL contains a real Page ID.
3. As a signed-in owner, I want to enter the newly created Page immediately after both local commands succeed.
4. As a signed-in owner, I want a staging failure shown on the dashboard so that I am not navigated into an incomplete workspace.
5. As a maintainer, I want Site and Page identities generated by their contracts so that browser code does not invent model IDs.
6. As a maintainer, I want empty Site and Page metadata represented consistently as `null` in command payloads and persisted resources.
7. As a maintainer, I want `home` to remain a Page slug rather than masquerading as a Page ID.
8. As a maintainer, I want local Zerospin staging to remain an immediate optimistic interaction with no pending presentation.

## Implementation Decisions

1. Canonical Zerospin extends nullable `primitives.text` descriptors to accept `defaultValue: null`; the identical core implementation is mirrored into `vendor/zerospin` for qrk.sh consumption.
2. A null default is valid only when `nullable: true`. It makes the caller payload field optional, causes payload validation to fill an omitted field with `null`, and remains present in the encoded descriptor. Non-nullable text continues to reject a null default at compile time.
3. `Site` becomes model version `2.0.0`.
4. The complete Site `1.0.0` definition remains in `Site` model history so existing `1.0.0` resources and mutations retain their original schema.
5. The current Site definition changes `slug`, `name`, and `description` to `primitives.text({ nullable: true, defaultValue: null })`. `userId` remains a required reference to User.
6. `createSite.payload.id` uses `Site.primaryKey({ autogenerate: true })`. Callers may omit it, while the validated command payload and emitted mutation always contain the generated Site ID.
7. `createSite.payload.userId` remains `User.primaryKey({ autogenerate: false })` and remains required.
8. `createSite.payload.slug`, `name`, and `description` use nullable text with null defaults, allowing the dashboard to omit all three fields.
9. The `createSite` program emits `Site.create("2.0.0", ...)`, its mutation schema uses `Site.createMutation("2.0.0")`, and the contract moves to version `1.1.0`.
10. `Page` becomes model version `2.0.0`.
11. The complete Page `1.0.0` definition remains in `Page` model history so existing `1.0.0` resources and mutations retain their original schema.
12. The current Page definition keeps required `siteId`, required `slug`, and required `pageType`. `title` and `description` become nullable text with null defaults.
13. `createPage.payload.id` uses `Page.primaryKey({ autogenerate: true })`. `siteId`, `slug`, and `pageType` remain required; `title` and `description` use nullable text with null defaults and may be omitted.
14. The `createPage` program emits `Page.create("2.0.0", ...)`, its mutation schema uses `Page.createMutation("2.0.0")`, and the contract moves to version `1.1.0`.
15. The compatible payload widenings and model mutation-version changes propagate the required `1.1.0` bump to `ownerFrontend`, the `owner` actor controller, and the `userAccount` controller.
16. The system version moves from `2.0.0` to the approved `3.0.0`. No mutation adapter is added because the Site and Page property changes widen persisted acceptance.
17. The dashboard page becomes a client component and keeps the click behavior inline in its existing `page.tsx`. No helper, child component, wrapper, named type, barrel, or new export is introduced.
18. The page reads the existing browser session with `useSession(ZerospinOwner)`. It derives the required domain User ID with `User.prefixId(session.browserUserController.userId)`, matching the Clerk User ID installed by `ZerospinOwnerProvider` and the deterministic User ID created during owner authentication.
19. Clicking “Create site” clears any prior inline error and stages `createSite` with payload `{ userId }`.
20. The button has no pending state under any circumstance. It is not disabled, its label remains “Create site,” and the page renders no loading text, spinner, or progress indicator while either Promise-shaped staging result resolves.
21. An encoded `createSite` `Left` leaves the user on the dashboard and renders its message beside the button in an inline element with `role="alert"`. No Page command is staged.
22. An encoded `createSite` `Right` supplies the generated `siteId` to `createPage`. The second payload contains `{ siteId, slug: "home", pageType: "split-scroll" }`; generated `id`, defaulted `title`, and defaulted `description` are omitted.
23. An encoded `createPage` `Right` navigates immediately to `/site/${siteId}/page/${result.right.payload.id}`. Navigation does not wait for automatic push, manual DevTools push, or server confirmation.
24. An encoded `createPage` `Left` leaves the user on the dashboard, retains the already staged Site, and renders the Page error through the same inline alert. No cross-command rollback is introduced.
25. Site creation does not stage `createGrid` or any Brick commands.
26. `SiteHeader` uses the current `siteId` and `pageId` route params for its Page link instead of hard-coding `/page/home`.
27. Bare `/site/:siteId` returns `notFound()` rather than redirecting to the fake Page ID `home`. The unused `DEFAULT_SITE_PAGE_ID` constant is removed; selecting a default Page by slug or relation is not added.
28. The existing Zerospin owner provider remains push-paused. This feature changes neither session configuration nor DevTools behavior.

## Testing Decisions

1. Canonical Zerospin core primitive tests verify nullable text accepts both a string default and a null default, omission decodes to `null`, explicit `null` remains valid, the descriptor encodes the null default, and non-nullable text rejects `defaultValue: null` at compile time.
2. Run canonical Zerospin `@zerospin/core` library, TypeScript, node-test, and lint targets through Nx before mirroring the core files into `vendor/zerospin`.
3. `packages/zerospin/src/siteContracts.workerd.spec.ts` is the focused qrk.sh integration seam; do not add web component-test infrastructure.
4. The workerd test stages `createSite` with only a valid owning `userId`, then stages `createPage` with the returned Site ID, `slug: "home"`, and `pageType: "split-scroll"`.
5. The workerd test verifies both encoded results are `Right`, their payloads contain autogenerated `sit_` and `pag_` IDs, and the optimistic Site and Page rows use those IDs with every omitted metadata field equal to `null`.
6. The workerd test verifies that omitting Site `userId` or Page `siteId` fails payload validation rather than generating or defaulting ownership.
7. The workerd test verifies the existing Site and Page owner guards reject resources that do not belong to the active actor.
8. Run `pnpm nx run @qrk.sh/zerospin:test:workerd`, `pnpm nx run @qrk.sh/zerospin:lint`, `pnpm nx run @qrk.sh/web:typecheck`, and `pnpm nx run @qrk.sh/web:lint`.
9. In the authenticated browser at `/morgs32`, verify the button always reads “Create site” and never becomes disabled or presents a pending indicator during either staging call.
10. Verify one successful click stages both resources and navigates directly to `/site/:siteId/page/:pageId` with the generated IDs.
11. Exercise each encoded staging failure and verify the dashboard remains mounted, exposes the error through `role="alert"`, and leaves the button available for another click. A Page failure retains the staged Site.
12. Verify the SiteHeader link preserves the concrete Page ID and bare `/site/:siteId` renders the Next.js not-found boundary.
13. Run `git diff --check` and confirm unrelated work in progress remains unchanged.

## Out of Scope

1. A site-creation form, authored initial metadata, slug generation, duplicate-site prevention, and creation limits are excluded.
2. Creating a default Grid or Brick is excluded.
3. Selecting a default Page for a Site by querying Page slug, adding a Site-to-default-Page reference, or changing public URL semantics is excluded.
4. Cross-command rollback when Page staging fails is excluded.
5. Waiting for push, server acknowledgement, or authoritative command finalization before navigation is excluded.
6. Loading states, transitions, disabled-button states, spinners, and pending labels for `stageCommand` are excluded.
7. Toast infrastructure, a new component-test harness, and new dashboard abstractions are excluded.
8. Changes to Zerospin session, push-queue, DevTools, or provider behavior are excluded.
9. Extending null defaults to scalar primitives other than text is excluded.
10. Cleanup or deletion of persisted local Zerospin state is excluded.

## Further Notes

1. The Zerospin first-party LLM wiki records “no pending UI for local staging” in `llm-wiki/patterns/react/no-pending-ui-for-local-staging.tsx`; implementation should follow that pattern even though `stageCommand` returns a Promise-shaped encoded Either.
2. `session.browserUserController.userId` is the Clerk identity string supplied to `ZerospinConfig`; it is not already a QRK User model ID and must be passed through `User.prefixId`.
3. Generated Site and Page IDs are read from their successful staged command payloads, not recomputed in the dashboard and not looked up from persisted tables.
4. `home` is the initial Page slug only. Every workspace route and Page-scoped control uses the generated `pag_` identity as `pageId`.
5. The canonical and vendored nullable-text primitive implementations must remain identical; no qrk.sh-only type shim or cast is permitted.
