# Publishing a Site and claiming a domain: Zerospin seam

Researched 2026-11-14 against QRK's current working tree, the sibling Zerospin source and QRK's installed Zerospin 44.0.3 declarations. This is a design investigation, not an implemented flow. The user has chosen an explicit publishing state, a shared Domains Service, a server-generated adjective and six-character suffix, and a new candidate on collision. The service and publishing state do not yet exist. [Current QRK registry](../../apps/zerospin/src/system.ts), [current publish contract](../../apps/zerospin/src/fresh/contracts/PublishSiteV1.ts), [prior domain research](./zerospin-server-domain-generation.md).

## What the two operations are doing

The previously proposed `publishSite` → `makeCommandOperation` → Domains external operation crosses two different seams. The first schedules an ordinary System command for another owner. The second records a server-only observation so the newly generated random value can be retained as an external outcome. The application is not calling a third-party provider merely because Zerospin calls this an external operation. [Recorded command](../../../zerospin/packages/sdk/skills/zerospin-external-work/references/recorded-external-work.md#L214), [external declaration](../../../zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md).

This is not a single request-and-reply operation. The recorded command's ID and payload are frozen, then delivered until the destination durably admits them. It supplies no destination outcome to the source, and an admitted destination can later refuse without undoing source success or automatically retrying. Returning the assigned domain to the Site aggregate would therefore require another deliberate command or another communication design. [Delivery and outcomes](../../../zerospin/packages/sdk/skills/zerospin-external-work/references/recorded-external-work.md#L229).

The other issue is durable entropy. Ordinary programs are shared across optimistic staging and server execution. Reconstruction of the same release can restore retained operations, but a new release without its own retained evaluation re-executes the original command against its own history. Fresh randomness inside that evaluation can choose another domain. An external request records its observed result as retained input for the continuation; the command's own framework-generated ID does not fill a domain payload. [Shared programs](../../../zerospin/wiki/adrs/020-shared-programs-and-portable-operation-declarations.md), [materialization](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/materializeCommandTx.ts), [command preparation](../../../zerospin/packages/core/src/contracts/prepareCommandOperation.ts), [external outcome retention](../../../zerospin/packages/system-worker/src/ServiceChain/recordExternalOutcomeAndAdmitCommandTx.ts).

There is no discovered supported ordinary-command callback that generates arbitrary business randomness once on the server, freezes it as command input, and supplies it unchanged on fresh-release replay. The older server adapter split was deliberately removed. Current `up` and `down` transform versioned payloads; they are not a one-time server enrichment. [Plan 259](../../../zerospin/wiki/archive/plans/259-plan-shared-program-command-operations.md), [payload adaptation](../../../zerospin/packages/core/src/contracts/decodeAndAdaptPayload/decodeAndAdaptPayload.ts).

## A simpler existing shape to evaluate

Zerospin's Shopping example already uses an aggregate external request that calls a System API command on a Service, awaits the Service's outcome, and lets the aggregate continuation apply that recorded response. Its promotion commitment request and continuation provide the concrete precedent; this is an existing mechanism, not proof that QRK's domain flow has been implemented or tested. [Shopping request](../../../zerospin/examples/shopping/src/zerospin/aggregates/user/contracts/utils/requestPromotionCommitment.ts), [Shopping aggregate continuation](../../../zerospin/examples/shopping/src/zerospin/aggregates/user/contracts/commitExternalPromotionV1.ts), [Shopping backend capability](../../../zerospin/examples/shopping/src/zerospin/ShoppingSystemApi.ts).

For QRK, a candidate design is:

1. `publishSite` records explicit `publishing` state and a same-aggregate external operation. The user-facing Site does not become published until completion.
2. Its backend request generates a candidate and calls a claims-free, System-granted Domains command. The Domains Service checks the candidate and Site's existing assignment inside its transaction; on a collision, the request tries a fresh candidate.
3. The successful Domain outcome is retained as the external observation. The aggregate continuation rechecks that the Site is still waiting for the corresponding publication and then finalizes it. If the Site was unpublished or a newer publication superseded the request, the continuation must not revive the old attempt.
4. Web resolves the reserved mapping to the Site, then reads the aggregate's published Site/Page and current snapshot. The mapping itself does not prove the Site is currently public.

This removes the initial recorded-command hop and the Domain-owned random external continuation from the earlier proposal. It still crosses two owners and needs backend System API authority, server configuration and an application-level idempotency rule. QRK's current backend config has no equivalent System API Layer; the Shopping example defines one. This is a proposed consumer design and a new trust boundary, not an already available QRK flow or an approved implementation. [QRK config](../../apps/zerospin/zerospin.config.ts), [Shopping config](../../../zerospin/examples/shopping/zerospin.config.ts), [Shopping System API live Layer](../../../zerospin/examples/shopping/src/zerospin/ShoppingSystemApiLive.ts).

## Retry and identity trade-off

The direct `SystemApi.executeServiceCommand` path waits for the destination's execution outcome, but each call is a fresh admitted System command and receives a new command ID. The service does **not** deduplicate these calls by a previously recorded command ID. If the claim commits but the external request loses its response or is retried, Domains must return the already assigned mapping for the same verified Site identity rather than create another. Enforce a single assignment per Site as well as uniqueness of the full hostname. The caller should generate another candidate only on a confirmed hostname collision, not on an ambiguous timeout; after timeout it must safely retry the idempotent Site claim. [Direct System admission](../../../zerospin/packages/system-worker/src/ServiceChain/admitDirectSystemServiceCommandTx.ts), [direct execution waits for outcome](../../../zerospin/packages/system-worker/src/executeDirectServiceCommand/executeDirectServiceCommand.ts), [Shopping retry note](../../../zerospin/examples/shopping/src/zerospin/aggregates/user/contracts/utils/requestPromotionCommitment.ts).

The continuation must validate the source aggregate, Site and pending publication before changing state. A status alone may not distinguish an old delayed response from a newer publication after an unpublish/republish; inspect whether the existing publication snapshot ID can identify the occurrence before introducing a separate ID. Any assignment that completed after unpublish can remain reserved for that Site while Web refuses public access. [Shopping stale-result checks](../../../zerospin/examples/shopping/src/zerospin/aggregates/user/contracts/commitExternalPromotionV1.ts), [current QRK snapshot payload](../../apps/zerospin/src/fresh/contracts/PublishSiteV1.ts), [existing unpublish command](../../apps/zerospin/src/fresh/contracts/UnpublishSiteV1.ts).

An alternative framework feature could make a recorded command request/reply with durable correlation, its same-ID retries and a retained destination outcome. Current `makeCommandOperation` promises delivery through admission, not that reply. This is a possible Zerospin design gap, not an implemented API; it would require an explicit outcome, recovery, version/replay, authority and cancellation design. Server-only entropy enrichment could also be designed upstream, but is a separate capability. Neither change automatically makes two owners' commits atomic. [Recorded work boundary](../../../zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md), [parallel-owner materialization](../../../zerospin/packages/sdk/skills/zerospin-parallel-models/SKILL.md).

## Evidence limits

The findings come from source and documentation inspection. No runtime test was performed for QRK's proposed flow, generated-domain collision behavior, inter-owner failure windows, current-version Service replay, or System API credentials. Match the exact installed packages and test the actual registered System and releases before implementation. No code, registry, storage, production service or account was changed by this research.
