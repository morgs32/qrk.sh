# Recorded commands with result continuations

Researched 2026-11-14 against the sibling Zerospin checkout and QRK's installed 44.0.3 declarations. This is source and historical research, not an implemented or runtime-tested design. The concrete question is whether a recorded command can retain its existing destination command ID across retries, wait for the destination's execution outcome, then deliver that outcome to a continuation on the originating owner.

## Answer

Yes, this is a coherent capability to design in Zerospin. It is not what the current `makeCommandOperation` does. Original execution freezes the destination command and its generated ID with the source outcome; the source then retries that exact command until the destination acknowledges **admission**. The current queue removes its pending delivery after that acknowledgement, and the initiating owner receives no success or refusal from destination execution. [Command preparation](../../../zerospin/packages/core/src/contracts/prepareCommandOperation.ts), [command queue](../../../zerospin/packages/system-worker/src/commandOperations/makeCommandDeliveryQueue.ts), [SDK guidance](../../../zerospin/packages/sdk/skills/zerospin-external-work/references/recorded-external-work.md).

The destination can already execute through a position and return the full, retained outcome for a specific release. Both Aggregate and Service VersionRepos have `awaitCommandResult`, and direct System execution uses the returned original-release outcome. Current recorded-command delivery does not connect that outcome to the source. [Aggregate result](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/awaitCommandResult/awaitCommandResult.ts), [Service result](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/awaitCommandResult/awaitCommandResult.ts), [direct Service command](../../../zerospin/packages/system-worker/src/executeDirectServiceCommand/executeDirectServiceCommand.ts), [direct Aggregate command](../../../zerospin/packages/system-worker/src/executeDirectSystemAggregateCommand/executeDirectSystemAggregateCommand.ts).

Awaiting an ordinary destination command's outcome does **not** await separately recorded commands or external work that it emitted. For example, if `Domains.assign` only schedules random-domain generation, its own successful outcome can be retained before a domain exists; returning that outcome alone cannot finish publication. A proposed native result continuation solves that command's request/reply and stable delivery identity, not the separate random-observation or later-work lifecycle. [SDK completion guidance](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/SKILL.md), [recorded-work boundary](../../../zerospin/packages/sdk/skills/zerospin-external-work/references/recorded-external-work.md).

## Did we consider it before?

There is evidence for deliberately separating delivery from execution, but the sources inspected do not establish that this exact native recorded-command continuation was proposed and rejected. Keep those conclusions separate:

1. [ADR 020](../../../zerospin/wiki/adrs/020-shared-programs-and-portable-operation-declarations.md) deliberately selected one shared ordinary program, original-only frozen destination commands and external work, and admission acknowledgement distinct from execution success. [Plan 259](../../../zerospin/wiki/archive/plans/259-plan-shared-program-command-operations.md) preserved the existing delivery machinery. Neither source explicitly analyzes adding a result continuation to `makeCommandOperation`.
2. [Shopping ADR 018](../../../zerospin/wiki/adrs/018-shopping-promotion-ownership-and-observation.md) and [Plan 239](../../../zerospin/wiki/archive/plans/239-plan-shopping-promotion-reservations.md) deliberately chose one-way recorded delivery for reserve/release/redeem, whose Service-owned state is separately observed without writing back to Cart/Purchase or coordinating retries. Commitment retained an external request because automatic checkout requires the exact Service decision before payment; the read-only projection can be stale and cannot authorize payment. The plan removed six response-only external contracts and added no framework delivery mechanism. This was a deliberate application decision using existing APIs, not evidence that a native framework request/result continuation was rejected.
3. [Plan 027](../../../zerospin/wiki/archive/plans/027-plan-actor-bound-async-contracts.md#problem-and-scope) explicitly excluded cross-owner async continuations from that scoped async-contract cutover. Exclusion from that plan is not a rejection of this proposal; its supported continuation was an owner-local command consuming a recorded external observation.
4. [ADR 012](../../../zerospin/wiki/adrs/012-opaque-external-work-and-originating-chain-continuations.md) made **external** work opaque and returned its observation to the originating owner; it rejected alternate addressed provider callbacks as duplicating routing and source identity. That rationale concerns the prior external-work design, not a decision that an ordinary destination command can never report its result.
5. [ADR 025](../../../zerospin/wiki/adrs/025-canonical-published-history-handoff.md) and [Plan 277](../../../zerospin/wiki/archive/plans/277-plan-canonical-chain-history-handoff.md) explicitly rejected lifetime per-command ID-location mappings for framework producers. Their existing delivery requirement was durable admission coverage, which an ordered per-producer checkpoint provides with less retained metadata. This is a real constraint a result-returning design must revisit, not a documented rejection of that design.

## The concrete missing correlation

Destination admission records the command at its own `aggregateIndex` or `serviceIndex`, but the recorded-command acknowledgement returns only the originating producer's covered `(sourceIndex, operationIndex)`. When an acknowledgement is lost, a repeated covered position returns the producer checkpoint without reconstructing the old destination index or comparing the replacement payload. The source's frozen delivery owns input immutability; this protocol can deduplicate without a lifetime ID directory. [Aggregate admission](../../../zerospin/packages/system-worker/src/AggregateChain/admitRecordedAggregateCommandTx.ts), [Service admission](../../../zerospin/packages/system-worker/src/ServiceChain/admitRecordedServiceCommandTx.ts), [source delivery validation](../../../zerospin/packages/system-worker/src/commandOperations/admitRecordedCommand.ts), [Plan 277 producer checkpoints](../../../zerospin/wiki/archive/plans/277-plan-canonical-chain-history-handoff.md#producer-checkpoints-and-admission-backpressure).

Meanwhile, `awaitCommandResult` requires the destination index and exact destination release. A stable `cmd_...` ID identifies the frozen command, but the current duplicate acknowledgement does not provide a durable way to recover its execution position once the initial reply is lost; finalized Chain input can also be handed off and pruned. The destination's ordinary System command contains no framework-owned reply address or source-operation link; `originCommandId` belongs to external continuation commands. [Service waiter](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/awaitCommandResult/awaitCommandResult.ts), [Aggregate waiter](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/awaitCommandResult/awaitCommandResult.ts), [System and external command schemas](../../../zerospin/packages/core/src/contracts/CommandSchema.ts), [history handoff](../../../zerospin/wiki/adrs/025-canonical-published-history-handoff.md).

## A possible framework direction

Offer an explicitly result-bearing recorded command operation, with one destination command frozen at source execution and one source-owner continuation receiving its destination's retained `outcome`. The source may expose the corresponding Site as `publishing` while work proceeds, but no source transaction or execution permit should be held while a different owner runs. This is a proposal: current SDK types and wire protocols do not implement it. [Current descriptor](../../../zerospin/packages/core/src/contracts/makeCommandOperation.ts), [original output preparation](../../../zerospin/packages/core/src/contracts/prepareCommandOperation.ts), [producer delivery](../../../zerospin/packages/system-worker/src/commandOperations/makeCommandDeliveryQueue.ts).

One implementation might retain a **bounded in-flight** correlation between source occurrence, its frozen child command, exact destination release, destination admission position and continuation until the result is durably returned; another could have the destination durably deliver the outcome back using trusted origin metadata. These are different potential designs to investigate, not a requirement for a permanent global ID directory. Preserve independent admission/execution: a destination business refusal is an `outcome` the continuation can handle, while transport, capacity, authorization and programming failures need distinct recovery semantics. A source delivery acknowledgement is not an outcome. [Outcome schema](../../../zerospin/packages/core/src/contracts/CommandOutcomeSchema.ts), [capacity and checkpoint rationale](../../../zerospin/wiki/archive/plans/277-plan-canonical-chain-history-handoff.md), [external outcome settlement](../../../zerospin/packages/system-worker/src/ServiceChain/recordExternalOutcomeAndAdmitCommandTx.ts).

Crash/retry seams to prove are: destination admitted but acknowledgement lost; destination outcome retained but source not notified; source observed result but continuation admission hits capacity; already-recorded result on restart; duplicate delivery; destination business refusal; source cancellation/unpublish and later republish; and version selection after canonical changes. External work already shows the useful pattern of recording an observation before capacity-dependent continuation admission and restoring it without rerunning a request. It does not automatically grant authority for a new ordinary-command result continuation. [Service observation retention](../../../zerospin/packages/system-worker/src/ServiceChain/recordExternalOutcomeAndAdmitCommandTx.ts), [Aggregate observation retention](../../../zerospin/packages/system-worker/src/AggregateChain/recordExternalOutcomeAndAdmitCommandTx.ts), [external continuation authority](../../../zerospin/wiki/adrs/023-flat-command-origins-and-claims-free-continuations.md).

Preserve producer order and idempotent delivery without waiting on another owner while holding a source model transaction. The existing delivery queue is earliest-first; making its single lane wait for execution could delay later commands. A dependency cycle or backpressure could also affect progress, but whether any proposed design deadlocks needs a concrete trace and test—this investigation found no documented incident or proof that request/result continuations are infeasible. [Command queue](../../../zerospin/packages/system-worker/src/commandOperations/makeCommandDeliveryQueue.ts), [source execution and delivery](../../../zerospin/packages/system-worker/src/AggregateChain/AggregateChain.ts), [64-command admission bound](../../../zerospin/packages/system-worker/src/ServiceChain/admitServiceCommands/appendServiceCommand.ts).

## Independent domain-generation issue

Reusing the destination command ID addresses delivery identity; it does not by itself record a random adjective/suffix as durable business input. Ordinary command callbacks currently receive their declared payload and model context, not a replay-stable random seed. If Domains generates fresh randomness during execution, a new release may evaluate the historical command again and select a different name. A retained external observation, a verified deterministic derivation from stable input, or a separately designed replay-stable entropy capability are different ways to address that issue; none is automatically provided by command-result continuations. [Command callback input](../../../zerospin/packages/core/src/contracts/types.ts), [Service materialization](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/materializeCommandTx.ts), [prior domain-generation research](./zerospin-server-domain-generation.md).

This review checked source, ADRs, archived plans, existing SDK guidance and current examples. It does not claim an exhaustive reconstruction of all earlier conversations, a tested request/reply protocol, a specific API shape, guaranteed cross-owner atomicity, or a production deployment.
