# Confirming a staged username command

Researched 2026-11-14 against the sibling Zerospin checkout and QRK's installed 44.0.3 packages. This investigates Service sessions; the same broad stages exist for Aggregate sessions. This is a source review, not a tested SDK change.

## Answer

The idea is close: the Node already knows whether each retained command has a matching final, and the originating Session receives a correlated final resolution. The Node does not normally delete a command when it finishes: it retains the original and a separate final. An absence alone cannot distinguish a command still in a tab's journal from a command that succeeded, failed, or whose completed local evidence was removed during recovery. [Node table](../../../zerospin/packages/core/src/ServiceNode/serviceNodeTables.ts), [Node coverage](../../../zerospin/packages/core/src/ServiceNode/ServiceNode.ts#L496), [Session view installation](../../../zerospin/packages/core/src/serviceSession/installServiceNodeView.ts#L94).

For the requested username flow, an SDK-owned reactive status for the particular staged command is a plausible direction using information Zerospin already transports. It would not inherently need a second server request or an external continuation. Exact behavior and API need design and testing, particularly recovery and the distinction between a successful command and the username currently shown after subsequent edits. It is not currently documented as a dedicated public command-status API. [Session submission and confirmation](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md), [React API exports](../../../zerospin/packages/react/src/index.ts).

## What happens to one save

1. `stageServiceSessionCommand` synchronously writes the session command and its optimistic model operations in one local transaction. Its success carries the `sessionId`, `sessionIndex`, and *local* staging result. At this point the Node coordinates and `serviceIndex` are null. A refusal during staging creates no staged command. [Public staging function](../../../zerospin/packages/core/src/serviceSession/stageServiceSessionCommand.ts), [staging transaction](../../../zerospin/packages/core/src/serviceSession/stageServiceSessionCommandTx.ts#L40), [synchronization handbook](../../../zerospin/fragment/content/handbook/sessions-and-synchronization.md#L24).
2. Background handoff lets the Node retain the original and allocate `nodeId`, `nodeIndex`, and `pushIndex`. Those coordinates establish retention, not a successful write on the Service. A lost handoff reply can leave the Session without coordinates even though the Node retained the original. [Node coverage](../../../zerospin/packages/core/src/ServiceNode/ServiceNode.ts#L496), [handoff guidance](../../../zerospin/fragment/content/handbook/sessions-and-synchronization.md#L62).
3. Admission and execution are separate. The Service's execution can accept or refuse the command. A final selected command carries the Service position, selected-resource delta, and a nullable failure. For the originating actor identity, the Service projection sends its execution failure when there is one. The Node records the final and applies its selected delta atomically. [Projection](../../../zerospin/packages/system-worker/src/serviceProjection/applyEvaluatedCommandsTx.ts#L62), [final retention](../../../zerospin/packages/core/src/ServiceNode/retainServiceFinalTx.ts#L106), [browser command schema](../../../zerospin/packages/core/src/contracts/BrowserCommandSchema.ts).
4. A Node view includes coverage for the originating Session's pending submissions. Its matching final resolution carries `serviceIndex` and `failure`. The Session validates the coordinates, installs the selected Node view and writes that resolution into the matching local command row in the same transaction. Normal queries then see the installed resources plus any other unresolved optimism. [Node coverage](../../../zerospin/packages/core/src/ServiceNode/ServiceNode.ts#L503), [Session installation](../../../zerospin/packages/core/src/serviceSession/installServiceNodeView.ts#L119), [local replay](../../../zerospin/packages/core/src/serviceSession/replayLocalServiceCommandsTx.ts).

Example: Alice stages `morgan`; it immediately appears locally. Bob's earlier claim wins on the Service. When Alice's final arrives, her original is no longer in the Node's unresolved overlay, but the correlated final is a **failure**; the view is reconciled. No pending optimism is not the same as a successful claim. The Node's outcome-prefix calculation counts matching finals, regardless of success or failure. [Unresolved overlay](../../../zerospin/packages/core/src/ServiceNode/ServiceNode.ts#L590), [outcome prefix](../../../zerospin/packages/core/src/ServiceNode/readServiceNodeOutcomeIndex.ts), [failure projection](../../../zerospin/packages/system-worker/src/serviceProjection/applyEvaluatedCommandsTx.ts#L75).

## What is visible today

- The Session's `nodeState` exposes `pushIndex`, `outcomeIndex`, `uncertainHandoffs`, connection state, and possible admission rejection. `outcomeIndex` is the contiguous Node producer prefix with matching finals, not a success count. `uncertainHandoffs` is the originating replica's pending handoff count; a command in another tab can still be in that tab before reaching the shared Node. The counts are useful progress evidence, but they do not identify a particular submitted command's verdict. [Node state](../../../zerospin/packages/core/src/aggregateSession/NodeState.ts), [prefix calculation](../../../zerospin/packages/core/src/ServiceNode/readServiceNodeOutcomeIndex.ts), [replica publishing](../../../zerospin/packages/browser/src/sessionReplica/makeServiceReplicaReceiver.ts#L296).
- The originating Session's `commands` row records `sessionIndex`, `nodeId`, `nodeIndex`, `pushIndex`, `serviceIndex`, and `failure`. In a normally installed matching view, `serviceIndex !== null` with `failure === null` is positive final evidence for that command; a non-null failure is a refusal. Before final installation both `serviceIndex` and `failure` are null, so failure alone is ambiguous. A completed row can be removed on checkpoint replacement; a missing row must not be interpreted as successful completion. [Session table](../../../zerospin/packages/core/src/serviceSession/serviceSessionRepoTables.ts), [view validation and replacement](../../../zerospin/packages/core/src/serviceSession/installServiceNodeView.ts#L94), [view resolution](../../../zerospin/packages/core/src/serviceSession/installServiceNodeView.ts#L211).
- The compact final does **not** contain the original successful command's full return value. A successful command can also legitimately have an empty selected delta. The UI must distinguish that verdict from what the latest model query displays, especially when a later edit or another tab's unresolved work is projected. [Browser command schema](../../../zerospin/packages/core/src/contracts/BrowserCommandSchema.ts), [two-replica recovery test](../../../zerospin/packages/core/tests/node-view-recovery.spec.ts#L1570), [empty-delta final test](../../../zerospin/packages/core/tests/node-view-recovery.spec.ts#L1838).
- The public session's initialized state contains the typed database and schema, including `commands`. The installed `@zerospin/react` package exports `useLiveQueryOnDb` through its wildcard subpath. The guide describes that lower-level hook for **diagnostic database reads**; ordinary `useLiveQuery` is typed around the application's models. A consumer can technically query the table, but relying on its deletion/recovery behavior as a product-level success contract requires an explicit SDK guarantee and coverage. [Session types](../../../zerospin/packages/core/src/serviceSession/types.ts#L89), [React package exports](../../../zerospin/packages/react/package.json), [query guide](../../../zerospin/fragment/content/guides/query-data.md#L90), [typed model query](../../../zerospin/packages/react/src/useLiveQuery.ts#L48).

## Candidate framework direction and limits

Expose a reactive, correlated status from the existing Session machinery: pending until the submitted `(sessionId, sessionIndex)` has a verified final; succeeded or refused when the matching resolution has been installed; unknown or interrupted if recovery or disposal loses the needed evidence. Keep the locally returned staging result separate. This is a proposal, not an existing API; it needs a precise lifetime, retry/recovery and failure contract and must not expose unrelated users' command failures. The Session needs to publish the final and installed resource view coherently. [Session receiver](../../../zerospin/packages/browser/src/sessionReplica/makeServiceReplicaReceiver.ts#L257), [failure observer](../../../zerospin/packages/browser/src/Node/makeSessionFailureObserver.ts).

If the UI wants the currently saved username rather than only the previous command's verdict, it must also account for later accepted or pending changes: a successful earlier save cannot guarantee a name stays current after a rename in another tab. A status based on the entire shared Node may unnecessarily wait for unrelated commands, whereas a particular submission's resolution can settle independently. Offline, blocked, rejected admission, reconnect, recovered journals, duplicate delivery, final-before-ack and a missing/replaced row need explicit tests. A selected session binds one exact Service release; its final describes that release and does not itself prove another release or its adopted canonical history has caught up. [Synchronization stages](../../../zerospin/fragment/content/handbook/sessions-and-synchronization.md#L24), [version selection](../../../zerospin/fragment/content/handbook/versioning-and-deployment.md#L53).

UI confirmation of a Service command is distinct from a `publishSite` guard in the separate User aggregate. A reactive command status can satisfy the creator-facing pending state without adding a network check, but it does not by itself establish an atomic cross-owner publication rule. [Shared owners](../../../zerospin/fragment/content/guides/shared-services.md#L47), [QRK publish guard](../../apps/zerospin/src/fresh/contracts/PublishSiteV1.ts#L70).
