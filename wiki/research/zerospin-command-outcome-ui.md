# Exposing a recorded command outcome to the UI

Researched 2026-11-14 against the sibling Zerospin source and QRK's installed 44.0.3 SDK guidance. The question is whether a creator can see that `Domains.assignDomain` failed, after `User.createSite` recorded it, without saving an assignment error on the Site. Domains, the proposed result-bearing command operation and its continuation do not exist in QRK today. This is source research and design analysis, not runtime verification.

## Answer

Zerospin already retains an executed command's result, including a business failure. That does **not** make a recorded child command's outcome a current, authorized, Site-addressable fact in the creator's browser. The framework could expose such a fact, but it needs a result correlation, a visibility policy and a lifecycle across retries, reconnects and history handoff. A Site error is not inherently required; it is one small way for QRK to express the actionable state through the existing model query. [Outcome schema](../../../zerospin/packages/core/src/contracts/CommandOutcomeSchema.ts), [session completion boundaries](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md), [actor projection](../../../zerospin/packages/system-worker/src/aggregateProjection/applyEvaluatedCommands/applyEvaluatedCommandsTx.ts).

For the stated requirement—show a Site-specific failure and Retry after reopening or on another device—the existing Site model route is the smaller application-specific choice. It should store a safe, actionable assignment failure, not raw framework exceptions or a duplicate history of delivery attempts. An opt-in framework operation-status view is worth considering if Zerospin has a broader requirement for durable user-visible status of asynchronous operations; the current UI requirement alone does not prove that broader API is needed. This is a recommendation, not a framework limitation requiring Site storage. [Selected actor visibility](../../../zerospin/packages/sdk/skills/zerospin-authorize-actors/SKILL.md), [YAGNI and coordination cost](../../../wiki/skills/use-morgs32-wiki-patterns/references/patterns/runtime/yagni-before-coordination.md).

## What exists now

1. The browser's `stageAggregateSessionCommand` commits optimistic work and returns session coordinates and a local result. It does not return the child's ID or prove canonical execution. The original addressed release retains an outcome `{ result: Success | Failure, finalizedAt }`; admission and execution are distinct. The current QRK `createSite` only creates a Site; recording a Domains command is a proposed change. [Completion boundaries](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md), [current createSite](../../apps/zerospin/src/fresh/contracts/CreateSiteV1.ts), [outcome schema](../../../zerospin/packages/core/src/contracts/CommandOutcomeSchema.ts).
2. Original source execution freezes a destination System command and ID once; delivery retries that same command until its admission is acknowledged. Acknowledgement is not the destination execution outcome, and the current recorded command operation does not return an outcome to User. The proposed new result-bearing operation would need to connect destination outcome to the originating continuation; this remains unimplemented. [Preparation](../../../zerospin/packages/core/src/contracts/prepareCommandOperation.ts), [delivery queue](../../../zerospin/packages/system-worker/src/commandOperations/makeCommandDeliveryQueue.ts), [recorded-work guide](../../../zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md).
3. Actor projection intentionally sends command failures only for a matching Actor-origin command; a recorded System command doesn't meet that condition. The public exposed-command table intentionally excludes private recipient and result columns. The live connection further checks claims, session name and Node before returning an owned failure, and the lifetime failure observer only reports originating command failures once. A remounted listener does not replay a historical failure. Therefore a Domains failure is not already an accessible User-session failure just because its outcome exists. [Aggregate projection](../../../zerospin/packages/system-worker/src/aggregateProjection/applyEvaluatedCommands/applyEvaluatedCommandsTx.ts), [public table](../../../zerospin/packages/core/src/aggregateSession/aggregateExposedCommandsTable.ts), [live delivery](../../../zerospin/packages/system-worker/src/aggregateSessionChain/AggregateSessionChain.ts), [failure observer](../../../zerospin/packages/browser/src/Node/makeSessionFailureObserver.ts), [completion boundaries](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md).
4. An internal `awaitCommandResult` can advance the Service and return an evaluated result for a known `serviceIndex` and exact release. The recorded-producer acknowledgement instead conveys coverage of a source position; a duplicate acknowledgement need not return a destination index. The frozen child ID alone is not an existing supported route to its destination outcome. [Service result waiter](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/awaitCommandResult/awaitCommandResult.ts), [Service recorded admission](../../../zerospin/packages/system-worker/src/ServiceChain/admitRecordedServiceCommandTx.ts), [producer checkpoint rationale](../../../zerospin/wiki/archive/plans/277-plan-canonical-chain-history-handoff.md#producer-checkpoints-and-admission-backpressure).
5. History handoff must not be confused with deletion of all historical evidence: the Service VersionChain prunes local rows after archive acknowledgement and its reader falls back to the VersionArchive. But an archive indexed by destination position does not itself create a Site-to-child lookup or authorize browser access. Producer checkpoints retain admission coverage rather than a lifetime command-ID-to-destination-position directory. [Archive handoff and reader](../../../zerospin/packages/system-worker/src/ServiceVersionChain/ServiceVersionChain.ts), [ADR 025](../../../zerospin/wiki/adrs/025-canonical-published-history-handoff.md), [producer checkpoints](../../../zerospin/wiki/archive/plans/277-plan-canonical-chain-history-handoff.md#producer-checkpoints-and-admission-backpressure).

## Framework option: expose an operation's outcome

One possible extension would let an authenticated User session query a **source-owned operation observation**, associated with the Site and operation occurrence, rather than querying Domains' private history directly. Its API shape, storage and policy are not established by the existing SDK. It would need to define all of the following:

- **Correlation and trusted authority.** Associate a specific source occurrence with its frozen child ID, destination release and execution position, and with the Site the actor is allowed to see. The source needs durable lost-ack recovery or an equivalent trusted destination-to-source result delivery. A caller-provided ID alone must not confer access. Authorization must use the authenticated Actor's actual selection/ownership, not the destination payload as proof. [Recorded admission](../../../zerospin/packages/system-worker/src/ServiceChain/admitRecordedServiceCommandTx.ts), [actor authorization](../../../zerospin/packages/sdk/skills/zerospin-authorize-actors/SKILL.md).
- **Result handoff.** Deliver the destination's original addressed-release outcome to the source durably and idempotently, without waiting in a source model transaction or blocking the ordered delivery lane. Preserve the distinction between admission and execution. Handling a destination outcome and committing a User continuation are separate recoverable steps; destination success is not proof that the continuation committed. A source continuation must still save the domain for the User aggregate to use it. [Delivery queue](../../../zerospin/packages/system-worker/src/commandOperations/makeCommandDeliveryQueue.ts), [existing external-outcome handoff](../../../zerospin/packages/system-worker/src/ServiceChain/recordExternalOutcomeAndAdmitCommandTx.ts), [prior result-continuation investigation](./zerospin-recorded-command-continuations.md).
- **Selected, safe output.** Decide what an Actor is allowed to see: a public status and sanitized failure may be appropriate; arbitrary destination result payloads, operational details and identity data are not automatically public. Current projection explicitly limits recipient/failure exposure and selected model rows. [Projection](../../../zerospin/packages/system-worker/src/aggregateProjection/applyEvaluatedCommands/applyEvaluatedCommandsTx.ts), [actor visibility](../../../zerospin/packages/sdk/skills/zerospin-authorize-actors/SKILL.md).
- **Durable view and retention.** Provide a query/snapshot and live updates to a reconnected session or another device, not only a toast to the browser that happened to initiate creation. Specify how it survives historical handoff and what happens when retained observations expire or the Site is removed. Reusing archived history requires an authorized indexed way to resolve the relevant occurrence; retained history by itself does not provide that query. [Actor history](../../../zerospin/packages/system-worker/src/AggregateActorVersionChain/AggregateActorHistory.ts), [Service archive lookup](../../../zerospin/packages/system-worker/src/ServiceVersionChain/ServiceVersionChain.ts), [completion boundaries](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md).
- **Retries and supersession.** A transport retry reuses the frozen child command; the user's Retry is a new business attempt. The view must identify the current attempt or otherwise define ordering so an old failure cannot replace a later success, and so an old success cannot misrepresent a newer attempt. Framework bookkeeping need only live as long as its explicitly defined guarantees, but a current-status UI requires a durable current result or other defined recovery. [Command preparation](../../../zerospin/packages/core/src/contracts/prepareCommandOperation.ts), [completion boundaries](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md).

This view could serve more use cases than Site domain assignment, but implementing it merely to avoid one Site field would add a cross-owner API, access boundary, retention policy and recovery contract. A dedicated authenticated Domains Service session exposing an authored assignment model is another option, but that exposes domain state rather than generic command outcomes and introduces a second session and selection; it also still needs an authored failure/retry lifecycle. [Service session and selection guidance](../../../zerospin/packages/sdk/skills/zerospin-author-feature/SKILL.md).

## Site-state option and failure boundaries

On an eventual **destination business failure**, the proposed continuation could record a small user-safe failure on the Site; on success it records the assigned domain. The existing authenticated User selection would make that state available through the normal live query. Retrying is an explicit new command, and its handling must prevent a late result from a previous attempt overwriting a newer address or failure. This is durable application state representing an unfinished, actionable assignment, not a copy of every command outcome. The exact model shape and retry concurrency policy remain design decisions. [QRK User actor](../../apps/zerospin/src/fresh/userActorV1.ts), [parallel-model invariant](../../../zerospin/packages/sdk/skills/zerospin-parallel-models/SKILL.md), [command outcomes](../../../zerospin/packages/core/src/contracts/CommandOutcomeSchema.ts).

Distinguish these cases:

- **Temporary delivery interruption:** an outstanding frozen command is retried by delivery machinery; absence of an address is not itself evidence of failure. [Delivery queue](../../../zerospin/packages/system-worker/src/commandOperations/makeCommandDeliveryQueue.ts).
- **Destination rejects or returns failure:** the proposed operation must deliver that final failure to the continuation before application state can represent it. Business collision handling can be inside the Domains command; a final rejection remains distinct from a retryable transport interruption. [Outcome schema](../../../zerospin/packages/core/src/contracts/CommandOutcomeSchema.ts).
- **Destination succeeds but the result/continuation is delayed or fails:** Domains may already own the address while User has not saved it. Result delivery and continuation recovery must be idempotent. A UI must not claim that the destination failed merely because the Site still lacks an address; if the continuation itself terminally fails, the proposed framework needs an explicit way to report or recover that separate failure. A Site field written only by that failed continuation cannot report its own inability to commit. [Result waiter](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/awaitCommandResult/awaitCommandResult.ts), [external settlement example](../../../zerospin/packages/system-worker/src/ServiceChain/recordExternalOutcomeAndAdmitCommandTx.ts), [prior design analysis](./zerospin-recorded-command-continuations.md).
- **Site deleted or assignment already succeeded before a delayed result:** the continuation must recheck current User state and apply an explicit no-longer-relevant policy; Sites and Domains remain separate transactions. Repeated attempts must also return or reconcile the existing mapping for the same Site. [Parallel model invariant](../../../zerospin/packages/sdk/skills/zerospin-parallel-models/SKILL.md), [recorded-work guidance](../../../zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md).

The proposed result-bearing operation must supply both success and business-failure outcomes to its continuation. It does not by itself wait for further commands or external operations emitted by the destination, and cannot by itself ensure a UI-visible outcome after an unrecoverable framework/continuation failure. [Prior request/result research](./zerospin-recorded-command-continuations.md), [completion boundaries](../../../zerospin/packages/sdk/skills/zerospin-submit-commands/references/completion-boundaries.md).

## Verification still needed

No proposed framework or QRK behavior was implemented or exercised. A future implementation needs tests for lost acknowledgements, original destination result and exact release, destination commit before response loss, repeated delivery, actor isolation and redaction, reconnect/new-device visibility, history handoff, retry races, deleted Sites, continuation failure, and recovery after the destination has already reserved an address. Test evidence must distinguish the contained harness from actual multi-owner delivery and browser synchronization. [Recorded-work guidance](../../../zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md), [authored behavior testing](../../../zerospin/packages/sdk/skills/zerospin-test-authored-behavior/SKILL.md).
