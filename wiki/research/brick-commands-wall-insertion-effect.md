# Brick-owned commands and shared Wall insertion

Researched 2026-11-12 against the local QRK and sibling Zerospin source. This is a design investigation, not an implementation or runtime verification. The user chose Brick-owned add and update commands with shared Wall insertion, and is open to considering a storage reset if the chosen design requires one.

## Effect services in Zerospin

An Effect service is a dependency identified by a `Context.Service`; an implementation is supplied through an Effect `Layer`. A command program can require such a service just as any Effect can. Zerospin's contract constructor preserves the Effect requirements of its guard and program in the contract's inferred execution requirements. Zerospin's tic-tac-toe example defines `ChooseComputerMove` as a service and supplies a `Layer`, although that example invokes it from an external request, not ordinary shared model mutation. [Effect services](https://effect.website/docs/v4/requirements-management/services), [Zerospin service example](../../../zerospin/examples/tic-tac-toe/src/chooseComputerMove.ts), [its external request](../../../zerospin/examples/tic-tac-toe/src/contracts/playExternalOMoveV1.ts), [ordinary contract constructor](../../../zerospin/packages/core/src/contracts/make/makeAggregateContractRelease.ts).

If ordinary Brick commands leave a `WallInsertion` service as an unmet requirement, browser execution needs a suitable implementation in the tab's session Layer for staging **and** in the executable SharedWorker registration's Layer for its checked Node replay. These are distinct runtimes: the tab stages locally, while the Node opens its own execution runtime from its registration. The connected session type derives its requirements from executable contracts. QRK currently passes a tab Layer containing connection configuration, and its worker registers the session definition without an application Layer; those entry points would need changing for an unprovided service requirement. Mock sessions and tests would also need appropriate wiring. [Session requirements](../../../zerospin/packages/core/src/sessionExecution/requirements.ts), [connected session](../../../zerospin/packages/browser/src/makeConnectedAggregateSession.ts), [Node runtime](../../../zerospin/packages/browser/src/Node/nodeExecution.ts), [worker documentation](../../../zerospin/fragment/content/reference/browser.md), [QRK tab layer](../../apps/app/zerospin/userApplicationLayer.ts), [QRK worker](../../apps/app/zerospin/node.worker.ts).

For backend execution, `makeConfig` accepts an application Layer and constructs a managed runtime; QRK currently provides no application Layer. Source inspection shows that the `makeConfig` required-Layer type derives requirements from owner/actor guards and external requests, but does not obviously collect ordinary contract-program requirements. A proposed service therefore needs explicitly verified backend configuration and missing-service coverage; do not assume the config's type signature enforces this wiring. This is a source observation, not a runtime-tested framework defect. [Config](../../../zerospin/packages/core/src/system/make/makeConfig.ts), [QRK config](../../apps/zerospin/zerospin.config.ts), [canonical command execution](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommand.ts).

Alternatively, the command can provide the service's Layer locally with `Effect.provide`; a fully satisfied Effect does not pass that service requirement on to its runtime hosts. Doing so fixes the implementation within the command's composition and makes it less useful as a runtime substitution seam. [Effect services](https://effect.website/docs/v4/requirements-management/services).

## Insertion and atomicity

Today the generic Add program verifies the Page ownership and Wall, checks the layout and fit, creates a Brick, and records Wall and Placement updates across breakpoints. These rules represent real Wall behavior regardless of which Brick command initiated the action. The selected design can place that behavior behind a shared insertion function or service called by each module's add command. The module owns its content payload and validation. [Current Add implementation](../../apps/zerospin/src/aggregates/user/contracts/wall/AddBrickContractV11.ts).

An Effect service does not automatically receive a command's current database or mutation permissions. Those are explicit callback inputs: reads use the declared models, and the program receives recording methods for its declared operation descriptors. A shared implementation must receive the invocation-specific data and permitted recording methods it needs, or return calculations for the caller to record. Its shape must be checked against actual Brick command call sites and model versions; wrapping the existing generic version machinery inside a service does not itself solve the typing problem. [Contract input types](../../../zerospin/packages/core/src/contracts/types.ts), [recording methods](../../../zerospin/packages/core/src/contracts/operationDescriptor.ts), [contracts and operations](../../../zerospin/fragment/content/handbook/contracts-and-operations.md).

Within one command evaluation, yielding recording methods constructs a checked batch; the owning workflow applies the batch in its transaction. Thus a Brick-owned add command can validate its own data and record both its Brick and shared Wall/Placement changes as one unit, provided the shared implementation participates in that command's recording rather than writing independently. A separate, later command would have a different lifecycle and does not itself establish atomic insertion. [Contracts and operations](../../../zerospin/fragment/content/handbook/contracts-and-operations.md), [session transaction](../../../zerospin/packages/core/src/aggregateSession/stageCommand/stageSessionCommandTx/stageSessionCommandTx.ts).

Logical ownership does not by itself settle where command files live. QRK's Zerospin package currently depends on Bricks; making Bricks import QRK's user-aggregate model definitions would reverse that dependency and create a package cycle. Any module-owned organization needs to account for that existing package direction. [Zerospin package](../../apps/zerospin/package.json), [Bricks package](../../apps/bricks/package.json).

## Execution and replay constraints

Session staging uses synchronous execution; a shared implementation used there must complete synchronously. Different implementations supplied to the browser and backend must preserve the same domain rules for equivalent inputs, or optimistic behavior and authoritative behavior can disagree. A pure deterministic calculation avoids provider/network dependencies during this command. [Session staging](../../../zerospin/packages/core/src/aggregateSession/stageCommand/stageAggregateSessionCommand.ts), [Effect synchronous execution](https://effect.website/docs/v4/getting-started/running-effects), [session runtime](../../../zerospin/packages/browser/src/makeConnectedAggregateSession.ts).

Fresh parallel-release evaluation executes that release's command behavior against its own state; reconstruction with retained release output restores recorded operations instead of re-running it. A dynamically supplied implementation is therefore part of the behavior an execution depends on, but a service name alone does not freeze historical behavior. Old generic command history and new command names still need a considered cutover or replay strategy. [Replay path](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts), [materialization](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts).

## Assessment

An Effect service **can** package shared insertion logic. Its distinctive benefit is choosing an implementation through a Layer, including substitution in tests or a genuinely different runtime. It also adds service identity, Layer wiring across each execution host, and an invocation-specific interface for the transaction and recording methods. An ordinary `Effect.fn` function can also be yielded from multiple Brick commands and does not itself introduce a service requirement. If insertion has one real implementation with no replaceable dependency, start by designing that function's concrete inputs and behavior; use a service if an actual caller needs implementation substitution or another demonstrated Effect dependency. This is a recommendation to test in design, not proof that a particular function signature works.

Before choosing either shape, examine at least Text and one other actual Brick add command, common authorization and layout needs, operation descriptor types, release history, and tab/worker/backend test execution. Preserve the user-only canonical registry rule. The user's willingness to reset does not identify a storage target or authorize an actual deletion in this research step.
