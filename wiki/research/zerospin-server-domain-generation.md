# Server-generated Site domains and command mapping

Researched 2026-11-14 against QRK's installed Zerospin 44.0.3 and the sibling Zerospin checkout. This is source research, not an implemented design. The proposed domain is a random adjective and six lowercase letters or digits, assigned on first publication and retained across unpublish/republish. QRK currently has no Domains Service. [QRK registry](../../apps/zerospin/src/system.ts), [current publish contract](../../apps/zerospin/src/fresh/contracts/PublishSiteV1.ts).

## Answer to the proposed mapping

The client does not need to send an empty string: the existing `publishSite` payload contains the Site ID, sizing choices and Page/snapshot IDs, but no domain field. A shared publish program can describe a recorded command to a Domains Service using the Site and aggregate identities. Optimistic staging validates that description but does not dispatch it; original server execution prepares and retains the destination command. The Domains Service then executes separately. [Publish contract](../../apps/zerospin/src/fresh/contracts/PublishSiteV1.ts), [command-operation guidance](../../../zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md), [original-only preparation](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/utils/prepareAggregateOutput.ts).

There is no current public hook found that takes an ordinary actor command after client staging, fills a placeholder with fresh server randomness, and durably freezes that transformed business input before all later execution and release replay. Zerospin deliberately removed its earlier public-program/server-contract-adapter split: an ordinary command now has one shared program. This may be the server mapping being remembered; its removal and rationale are explicit in [Plan 259](../../../zerospin/wiki/archive/plans/259-plan-shared-program-command-operations.md) and [ADR 020](../../../zerospin/wiki/adrs/020-shared-programs-and-portable-operation-declarations.md).

The current `up` and `down` callbacks are **contract-version payload adapters**. They run when decoding an input at a different contract version, including replay. They do not rewrite the retained command bytes, nor do they automatically freeze a newly generated random value. Using a fresh NanoID in such an adapter can produce a different value in another evaluation. They are not the once-per-publish server enrichment described above. [Contract upgrade signature](../../../zerospin/packages/core/src/contracts/make/upgradeAggregateContractRelease.ts), [version adaptation](../../../zerospin/packages/core/src/contracts/decodeAndAdaptPayload/decodeAndAdaptPayload.ts), [optimistic replay](../../../zerospin/packages/core/src/sessionExecution/replayAggregateCommandTx.ts), [handbook](../../../zerospin/fragment/content/handbook/contracts-and-operations.md).

## Why the random value needs evidence

The existing `NanoIdFactory` calls `nanoid()` when asked; it is not a replay-stable business-value factory. A shared ordinary program can be evaluated for browser staging, rebasing and server execution. A release restoring its own retained evaluation reapplies recorded output, whereas a different release without its own retained evaluation can run its own program over the admitted input and prior release-local state. Generating a new random domain directly inside that program therefore does not by itself make the same address an input to every release's replay. [NanoIdFactory](../../../zerospin/packages/core/src/utils/NanoIdFactory.ts), [ordinary program decision](../../../zerospin/wiki/adrs/020-shared-programs-and-portable-operation-declarations.md), [Service materialization](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/materializeCommandTx.ts), [Service replay](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/replayCommands/replayCommand.ts).

The framework does allocate and freeze a destination **command ID** during original preparation, and retries delivery with the same complete command. That does not automatically generate or persist an adjective or NanoID inside the command's **payload**. Command programs receive payload, claims, model reads and operation methods, not an automatically supplied recorded-command ID from which this particular domain can be derived. [Command preparation](../../../zerospin/packages/core/src/contracts/prepareCommandOperation.ts), [command callback input](../../../zerospin/packages/core/src/contracts/types.ts), [delivery semantics](../../../zerospin/packages/sdk/skills/zerospin-external-work/references/recorded-external-work.md).

## Existing ways to supply the value

1. **Generate on the client and include the candidate in the command.** The candidate is frozen as input, so it can be evaluated/replayed consistently without a server-only mapping. It does not meet a requirement that the client supply no generated domain or that the server control generation. A Domains Service must still check global uniqueness; a preflight availability check is not a reservation. If its destination command refuses a collision, recorded-command transport retry does not regenerate a candidate or change source success. [Command inputs](../../../zerospin/fragment/content/handbook/contracts-and-operations.md), [delivery semantics](../../../zerospin/packages/sdk/skills/zerospin-external-work/references/recorded-external-work.md).
2. **Derive candidates deterministically in the Domains Service from a stable input.** For example, the existing randomly generated Site ID can seed a stable, DNS-safe candidate sequence, and a claims-free System command can use the service's current rows to choose the first unclaimed candidate. The client sends no domain string; a hash-derived candidate uses randomness already present in the Site ID rather than fresh, independently generated server NanoID randomness. The exact alphabet, adjective selection, distribution, bounded collision handling, versioned algorithm and replay against differing prior release states require design and verification. Consistency across independently materialized releases is not automatic if historical state or the algorithm differs. [QRK Site ID creation](../../apps/app/app/%5Busername%5D/%28dashboard%29/page.tsx), [NanoIdFactory](../../../zerospin/packages/core/src/utils/NanoIdFactory.ts), [Service execution context](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/utils/evaluateServiceCommand.ts), [parallel models](../../../zerospin/packages/sdk/skills/zerospin-parallel-models/SKILL.md).
3. **Record a server-generated observation.** The Domains Service command can record a same-family Service external operation. Its backend `request` generates the random candidate; the recorded `externalOutcome` is later passed to its continuation. The continuation checks the Service's current mapping and writes a free candidate. This uses an actual external contract/continuation even if no third-party provider is called, and the address becomes available asynchronously. On collision, the continuation would need to record a new generation attempt or apply another explicitly designed policy; merely refusing does not create one. The first recorded observation is retained before completion admission; a process interruption before observation may rerun the request. A recorded observation is input to historical continuation replay. [External definition](../../../zerospin/packages/core/src/contracts/defineServiceExternalContract.ts), [backend request and continuation](../../../zerospin/packages/core/src/contracts/make/makeServiceExternalContractRelease.ts), [observation retention](../../../zerospin/packages/system-worker/src/ServiceChain/recordExternalOutcomeAndAdmitCommandTx.ts), [recorded-work guide](../../../zerospin/packages/sdk/skills/zerospin-external-work/references/recorded-external-work.md).
4. **Add an upstream one-time server enrichment capability.** A new Zerospin API could be designed to accept the simple client command while freezing server-generated business data durably for later evaluation and cross-release replay. No such API was found in the inspected current declarations. Its transaction, validation, collision, origin, replay and offline behavior would be framework design work, not an existing mapper or an approved implementation.

The approaches are options, not a recommendation that the user has approved an additional subsystem. In particular, an external operation is not the ordinary recorded System command previously chosen for synchronizing usernames.

## Publication and visitor resolution

The User aggregate's publication and the Domains Service mapping are separate owner transactions. A publish command can finish before its recorded Domains command executes; destination admission also does not guarantee destination execution succeeds. If the destination refuses a one-candidate collision, the source publication is not rolled back. The UI and failure/retry behavior need an explicit decision. [Cross-owner commands](../../../zerospin/packages/sdk/skills/zerospin-external-work/references/recorded-external-work.md), [current publish command](../../apps/zerospin/src/fresh/contracts/PublishSiteV1.ts).

For a visitor, the configured local wildcard sends `gentle-a7b2c3.qrk.localhost` to Web. Web can look up the exact label in the Domains Service using its server-only System API, then read the identified User aggregate and Site. The final Page read must still check published Site, published Page and current snapshot pointer; it must not treat the retained domain mapping as publication authority. This keeps a reserved domain unavailable immediately after a committed unpublish. The current reader uses a Clerk username lookup instead; changing that is proposed work, not present implementation. [Local wildcard configuration](../../package.json), [current reader](../../apps/web/library/readPublishedPage.ts), [service query](../../../zerospin/packages/system-worker/src/ServiceVersionRepo/executeServiceQuery/executeServiceQuery.ts).
