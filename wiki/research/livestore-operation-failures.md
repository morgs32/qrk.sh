# LiveStore and model-level operation failures

Researched 2026-11-14 against LiveStore's public 0.5.0 documentation and repository, and the sibling Zerospin checkout. This is source research, not a runtime experiment. The question is whether LiveStore supplies model-level failure fields comparable to the proposed Zerospin `failedAt` and `failure` fields for external work and failed continuations.

## Findings

- **No documented equivalent found in the inspected LiveStore surfaces.** LiveStore's side-effects guide is a TODO: it lists client/session/global execution and rollback/rebase as topics to document, rather than specifying a built-in operation with automatic error fields on a row. This is a scoped finding about the docs and sources examined, not proof that no other extension exists. [LiveStore side-effects pattern](https://docs.livestore.dev/patterns/side-effects/).
- LiveStore applications define event payloads and SQLite table columns; committed events are materialized into rows, which can then be queried reactively. Its schema documentation explicitly declares `createdAt` in example schemas, and its changelog shows an explicit `createdAt` with a SQLite default. These examples do not establish universal implicit timestamp or failure fields. [Schema definitions](https://docs.livestore.dev/building-with-livestore/state/sqlite-schema/), [Store API](https://docs.livestore.dev/api/livestore/classes/store/), [changelog schema example](https://github.com/livestorejs/livestore/blob/main/CHANGELOG.md).
- LiveStore also exposes framework-level status, but for different facts: `store.syncStatus()` reports synchronization between a client session and leader, and `syncStatusStream()` streams changes. It is not a result for a particular external operation. LiveStore's runtime spec also identifies `MaterializeError` as a terminal shutdown cause in its session/leader boundary, and its changelog describes stopping backend-head advancement when materializers crash. These describe runtime health, not a field automatically written to a business row. [Store sync status](https://docs.livestore.dev/api/livestore/classes/store/#syncstatus), [runtime error taxonomy](https://github.com/livestorejs/livestore/blob/main/context/02-system/04-runtime/spec.md#boundary-error-taxonomy), [materializer crash fix](https://github.com/livestorejs/livestore/blob/main/CHANGELOG.md).
- LiveStore's state-machine pattern describes listening to query results and emitting events, with side effects committing further mutations. That is an application-authored pattern, not evidence of a built-in durable external-command continuation or automatic continuation-failure field. The Store API says `events()` streams only backend-confirmed events and documents limitations. [State-machine pattern](https://docs.livestore.dev/patterns/state-machines/), [Store event stream](https://docs.livestore.dev/api/livestore/classes/store/#events).

## What the timestamp analogy means for Zerospin

Zerospin does provide framework-defined `createdAt` and `updatedAt` attributes. Its model factory adds them, and the operation application code derives them when applying a recorded create or update operation. [Model declarations](../../../zerospin/packages/core/src/models/make/makeModelVersion.ts), [operation application](../../../zerospin/packages/core/src/contracts/applyOperationTx.ts).

The proposed failure fields differ in a significant but not necessarily prohibitive respect: the continuation may have produced no committed model operation. Currently Zerospin executes the program under a savepoint; recognized failure rolls back those changes and yields a failed command outcome, whereas other defects can abort materialization. Existing framework-controlled timestamp behavior does not itself record a failure update. [Command execution](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts), [parallel model invariant](../../../zerospin/packages/sdk/skills/zerospin-parallel-models/SKILL.md).

A framework could be **redesigned** to associate an external occurrence with an authorized target model/resource, retain a separate failure write after rollback, and expose the resulting fields to selected sessions. That would be new behavior: its replay/provenance, resource identity, error sanitization and access policy need definition. The mechanism would need a rule for concurrent operations and retries on the same row, since one `failure` value could otherwise overwrite another or be cleared by the wrong attempt. Storage unavailability or an unexpected materialization defect require their own recovery semantics; an owner-model field cannot be updated while its required write path is unavailable. Whether such a write can unblock a given failure, and how it participates in command history, are open design questions—not a proof it is impossible. [Command execution](../../../zerospin/packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts), [existing external continuation API](../../../zerospin/packages/core/src/contracts/make/makeAggregateExternalContractRelease.ts), [external operation recovery](../../../zerospin/packages/system-worker/src/externalOperations/makeExternalOperationQueue.ts).

For ordinary external work today, the request returns an external outcome; a continuation program receives it and can explicitly record a model update. The Shopping payment example maps an external failure to `needs_reconciliation` on the purchase. This covers a request failure when the continuation can commit, not an unexpected failure of the continuation itself. [External release API](../../../zerospin/packages/core/src/contracts/make/makeAggregateExternalContractRelease.ts), [payment continuation](../../../zerospin/examples/shopping/src/zerospin/aggregates/user/contracts/processExternalPaymentV1.ts).

The proposed result-bearing `makeCommandOperation` for Domains is also not currently implemented, and its result and continuation-failure behavior would need a design independently of the existing external-work API. [Prior research](./zerospin-recorded-command-continuations.md).

## Limits

The findings above use current public LiveStore sources; its documentation itself says some sections remain in progress. No LiveStore package was installed or executed, no exhaustive audit of every community extension was attempted, and no Zerospin or QRK behavior was changed. [LiveStore documentation status](https://docs.livestore.dev/), [LiveStore side-effects guide](https://docs.livestore.dev/patterns/side-effects/).
