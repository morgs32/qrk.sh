# json-render prior art for QRK Bricks

Researched 2026-11-11 against application source, package manifests, and project documentation.

## Closest examples

- **Vercel Labs Dashboard is the closest reference for saved Placements.** The reference app stores a JSONB spec per widget alongside its position. Its editor streams a spec, persists the completed spec, loads the stored spec on return, and gives the previous spec to the generator when editing. Dragging updates widget order separately. QRK uses the same broad division between persisted presentation and layout, with its own Brick state and breakpoint Walls. This is upstream example code. - **LLM Gateway Canvas is the closest workspace example.** Its private `@llmgateway/canvas` package compiles and exports `./catalog`, `./templates`, and `./spec`. The Next app accepts a template, generated output, or hand-edited JSON and renders through its registry. A native WebView preview consumes the same spec validator. Web and WebView use separate chart registries over a shared base so the web host can load charts dynamically. This demonstrates shared spec code with host-owned rendering composition. The product docs describe editing and exporting the iOS preview and say it stays outside conversation history. - **k8ordo is the closest published design-system package.** `@k8ordo/ui/json-render` exposes the server-safe catalog, prompt rules, validation, and typed authored specs. `@k8ordo/ui/json-render/registry` exposes its React renderer and registry. The export map targets separate compiled files. The library publishes component Storybook stories. Upstream `@json-render/shadcn` uses a similar separate `./catalog` export. This is precedent for distinct import surfaces within a package and for a library that ships with a component Storybook. ## Two smaller precedents

- **LazyLabel renders authored application screens from checked-in JSON.** Its Ask page imports a static spec, passes separately managed state and action handlers, and renders with a registry combining shadcn components with its own React components. This is a useful example of JSON specs as normal application UI. [Ask page](https://github.com/rodrigotriboni1/lazylabel/blob/98c321c9e701a13d23eeeb2da959440b6aa9df68/codigo/lazylabel/frontend/src/pages/AskPage.tsx) · [Registry and renderer](https://github.com/rodrigotriboni1/lazylabel/blob/98c321c9e701a13d23eeeb2da959440b6aa9df68/codigo/lazylabel/frontend/src/ui/SpecView.tsx#L8-L17)
- **AgentWorks documents a saved-format change.** Its chat visual renderer compiles json-render streams into specs and displays them through a custom registry. The change kept older saved visuals as collapsed source when they could no longer render. It illustrates that storing visual input makes renderer compatibility a product decision. [Compiler](https://github.com/manishiitg/agentworks/blob/b047fb2f1f936333fae6a169434fdf4293c59d12/frontend/src/components/ui/chatVisualSpec.ts) · [Registry and source fallback](https://github.com/manishiitg/agentworks/blob/b047fb2f1f936333fae6a169434fdf4293c59d12/frontend/src/components/ui/ChatVisualRenderer.tsx#L20-L40) · [Saved-format change](https://github.com/manishiitg/agentworks/pull/1338)

## What carries over to QRK

The public examples support durable generated specs, authored defaults through the same renderer, and explicit exports separating catalog code from React. The closest public evidence spans separate projects. Independent specs per breakpoint Placement, shared Brick state, and editor-to-public rendering are QRK's combination. QRK's `specRevision` protects concurrent edits and generation. The published snapshot stores the spec and variant ID alongside the Brick's module ID. Compatibility when a future catalog changes remains a QRK decision. [Placement model](../../apps/zerospin/src/aggregates/user/models/placement/PlacementV1.ts#L19) · [Revision checks](../../apps/zerospin/src/aggregates/user/contracts/brick/GenerateBrickSpecExternalV2.ts#L104) · [Published snapshot](../../apps/zerospin/src/aggregates/user/snapshots/pageSnapshotSchemaV4.ts#L47)

For the proposed extraction, a useful check is to render an already saved Link spec with the same extracted renderer in App and Web, then render the authored default through it in Storybook. That checks the saved contract and the import direction together. Compiled exports are an option demonstrated by the package examples. QRK can choose the package layout and build strategy independently.
