# Plan 075 — Configured aggregate base versions

**Date:** 2026-09-08
**Status:** Implemented; runtime suites passed. Broad typecheck gates remain blocked by unrelated workspace failures, so this plan remains active.

Source: [Spec 075](../archived/075-spec-configured-aggregate-base-versions.md). Prerequisite: the existing [typed configuration design](../specs/074-spec-typed-system-config.md) and its implemented `system.config(...)`/generated Worker entry.

## Outcome and constraints

1. Require `system.config({ aggregates: { [aggregateName]: { canonical } }, seeds? })`. Configuration selects the desired aggregate base without changing the immutable System spec. A configuration-only deployment requires no System or aggregate execution-version bump.
2. AC adopts the configuration of its executing bundle during activation. New chains start at that base; existing chains retain their applied base until a checked, forward-only comparison succeeds after activation. Skipped configurations require no intermediate promotions.
3. Preserve the existing system-version feed for supported-materializer enrollment, complete command occurrences, strict disposition comparison, concurrent admission, direct-result recovery, and frontend version binding. Preserve current subscription activation; this plan moves no subscription or trust-boundary responsibility.
4. Remove manual aggregate cutover RPCs. Service cutover remains unchanged. Add no configuration feed, deployment coordinator, live configuration reload, rollback, inspection RPC, or new helper/type abstraction. Extend existing factories, types, Effects, transactions, and test suites.
5. Implement on `main`, preserving unrelated WIP. Changed AC fixed storage requires empty storage; this plan authorizes no reset. Use freshly provisioned test storage and request approval for any existing state that must be reset. Do not add migration or compatibility paths.

## 1. Extend configuration without changing authored definitions

1. Update `ISystem.config` and `ISystemConfig` in Core's existing system types. Make the config argument and `aggregates` record required, including `{ aggregates: {} }` for aggregate-free Systems. Each value is an inline readonly `{ canonical: string }` shape; keep seeds optional with the existing environment normalization and inference.
2. Map configuration keys from the `AGGREGATES` generic already owned by `ISystem`, not `keyof system.aggregates`: the public aggregate registry currently intersects an open string record. Append an aggregate-name generic to the existing `ISystemConfig` after its current generic parameters, defaulting to `string` for erased loaders, and pass `keyof AGGREGATES & string` from `ISystem.config`. Do not widen the concrete configuration's keys or replace seed types with broad assertions.
3. Extend `makeSystem`'s existing synchronous config method and `ZerospinConfigSchema`. Retain strict input-shape validation. Validate exact key coverage against the receiving System, reject unknown keys and malformed entries, and require every base string to equal the aggregate's current version or an entry in its historical definitions. Validate the live aggregate's version/history shape before membership checks so invalid default exports produce configuration failures. Check membership synchronously; do not execute `getVersion()` Effects, seeds, or runtime startup while constructing configuration.
4. Put complete configuration membership validation in the existing `ZerospinConfigSchema` so both construction and CLI loading enforce it. Invoke validation before returning the typed configuration without returning a decoded value that erases factory inference. Retain source-context errors in `loadZerospinConfigFn`; validation must also reject invalid hand-built default exports.
5. Copy and freeze the owned settings record and each settings entry. Preserve `config.system` identity and the current seed normalization/freezing. Later mutation of caller-owned settings must not change the returned config.
6. Do not add `canonical` to aggregate factories, historical definitions, snapshot views, `makeSystemSpec`, or `SystemSpecSchema`. Prove two configurations of the same System serialize to the same System spec and reuse the same published system-version row.

## 3. Persist configured intent and schedule AC recovery

1. Add `desiredBaseAggregateVersion: primitives.text()` and `cutoverFailure: primitives.text({ nullable: true })` to AC's existing `chainState`. Keep `baseAggregateVersion`, `systemVersionIndex`, and halt fields. Add no retry counters, config revisions, comparison checkpoints, or history tables.
2. Import named `config` at the AC activation boundary and read `config.aggregates[key.aggregateName].canonical`. Retain an alarm lease named `cutover` before committing initialization or changed intent. Keep the independent admitted-command delivery lease.
3. Initialize an absent row with applied and desired versions both set to the configured base, `cutoverFailure: null`, and the existing initial cursor/halt values. On conflict, update only desired intent and clear `cutoverFailure` if the desired value changed. Preserve applied base, existing same-intent failure, feed progress, and invalidation history. Use a single atomic upsert with a conditional failure assignment; no read-before-write initialization race or schema fallback.
4. Preserve the existing subsequent system-version subscription. It may enroll destinations, but neither feed receipt nor subscription may overwrite desired/applied bases. Subscription failure must leave committed initialization/intent and retained recovery intact.
5. Register the existing `cutover` Effect lazily with `this.alarmRegistry` during AC construction. Registration does no storage work. The operation reads durable intent when run; it does not capture a destination at construction time. Supply the existing db/key, alarm registry, and source-bound system-version subscriber.
6. Keep the inherited alarm dispatcher. Do not call comparison from `onDOActivation`, feed receipt, admission, or a new RPC. The first empty-chain reconciliation takes the already-applied path without materializer lookup.

## 4. Convert cutover into complete local recovery

1. Change the existing `cutover` Effect to return `void` and accept the existing bound dependencies plus `alarms`; remove its caller-supplied `destinationAggregateVersion`. The effect itself owns its `cutover` lease. Keep comparison and failure handling in this existing module, with the existing promotion/invalidation transaction modules owning their commits.
2. Renew the lease before each recovery attempt. Load the applied and desired versions. Equality clears any current-intent failure conditionally and releases the lease without remote work. A different destination that is not numerically newer under the existing comparator records a blocked failure, releases the lease, and returns normally.
3. An already-invalidated desired candidate records its retained invalidation reason and releases the lease without flushing. These settled branches must remain cheap when unrelated queues cause the registry to run again; they must not keep an alarm alive solely for the blocked request.
4. For eligible work, catch up the system-version feed before enrollment validation. Reload applied/desired state after this await and restart evaluation if either changed. Use the existing supported-version lookup and subscriber validation. Missing enrollment after catch-up or other infrastructure failures leave recovery pending; they cannot authorize promotion or invalidate the candidate.
5. Sample the highest retained `admittedCommands.aggregateIndex` and its command ID. At zero, use the existing promotion transaction without resolving materializers. Otherwise retain concurrent `VersionedAggregateRepo.getRepo(...).flush(n)` calls and exact checkpoint identity/hash checks. Do not change VAR execution, service observations, or finalized publication.
6. Extend `commitPromotionTx` and `commitInvalidatedCandidateTx` to recheck both sampled versions in their existing `makeTx`/`AggregateChainDb.Tx` transactions. Recheck candidate existence/invalidation as well. Changed intent or changed applied base returns `pending` without changing either candidate state or diagnostics. The outer recovery reevaluates current intent.
7. Successful promotion changes the applied base and clears `cutoverFailure` atomically. Divergence writes candidate invalidation and the matching chain failure atomically. Retain existing invalidation timestamps, checkpoint, and reason semantics. A candidate invalidated concurrently cannot be promoted or silently reset.
8. Serialize persisted diagnostic errors with the existing `ZerospinError.stringify` convention. Condition diagnostic writes on both sampled applied/desired versions so old failures cannot overwrite a newer request. Persist blocked/invalidated failures before releasing the lease. Keep single conditional writes direct; use the existing transaction convention only for coupled reads/writes or multiple atomic mutations.
9. On transport, protocol, or persistence failure, retain the lease, attempt to persist the current-intent diagnostic, and propagate failure through the existing alarm dispatcher. If diagnostic persistence also fails, preserve the operation failure and recovery. Never release the lease unconditionally in a finalizer. Interruption must leave recovery scheduled.
10. Release only after current intent is settled: already applied, promoted, blocked, or invalidated. Keep recovery retained for superseded or interrupted work. A restart after promotion but before release completes through equality. Other alarm registrations continue independently; do not modify the shared registry or add a chain-wide lock across remote calls.
11. Continue selecting only `baseAggregateVersion` in direct execution and frontend/base selection. Existing Repo table inspection automatically exposes the two added columns; no new UI or inspection endpoint is needed.
