# Dashboard one-click site creation design

**Date:** 2026-07-17
**Status:** Approved for planning

## Problem Statement

The authenticated dashboard renders a “Create site” button that performs no action. The current `createSite` contract also requires the browser to provide a Site ID and three text values even though a new site should begin without authored metadata. This prevents the dashboard from creating a site with one local action and navigating directly into its workspace.

## Solution

Make Site metadata nullable with null defaults, move Site ID generation into the `createSite` contract, and keep the owning User ID as the only required browser input. The dashboard stages that command through its existing Zerospin owner session and navigates immediately from the successful staged result. Local staging never produces pending UI; an encoded staging failure remains on the dashboard as an inline error.

## User Stories

1. As a signed-in owner, I want one click to create a site without completing a form.
2. As a signed-in owner, I want to enter the newly created site workspace immediately after local staging succeeds.
3. As a signed-in owner, I want a staging failure shown on the dashboard so that I am not navigated to a site that was not created locally.
4. As a maintainer, I want Site identity generated by the contract so that browser code does not invent model IDs.
5. As a maintainer, I want empty Site metadata represented consistently as `null` in the command and persisted resource.
6. As a maintainer, I want local Zerospin staging to remain an immediate optimistic interaction with no pending presentation.

## Implementation Decisions

1. `Site` becomes model version `2.0.0`.
2. The complete Site `1.0.0` definition remains in `Site` model history so existing `1.0.0` resources and mutations retain their original schema.
3. The current Site definition changes `slug`, `name`, and `description` to `primitives.text({ nullable: true, defaultValue: null })`. `userId` remains a required reference to User.
4. `createSite.payload.id` uses `Site.primaryKey({ autogenerate: true })`. Callers may omit it, while the validated command payload and emitted mutation always contain the generated Site ID.
5. `createSite.payload.userId` remains `User.primaryKey({ autogenerate: false })` and remains required.
6. `createSite.payload.slug`, `name`, and `description` use `primitives.text({ nullable: true, defaultValue: null })`, allowing the dashboard to omit all three fields.
7. The `createSite` program emits `Site.create("2.0.0", ...)`, and its mutation schema uses `Site.createMutation("2.0.0")`.
8. `createSite` moves to contract version `1.1.0`. The compatible payload widening and Site mutation-version change propagate the required `1.1.0` bump to `ownerFrontend`, the `owner` actor controller, and the `userAccount` controller.
9. The system version moves from `2.0.0` to the approved `3.0.0`. No mutation adapter is added because the three Site property changes widen persisted acceptance from required text to nullable text.
10. The dashboard page becomes a client component and keeps the click behavior inline in its existing `page.tsx`. No helper, child component, wrapper, named type, barrel, or new export is introduced.
11. The page reads the existing browser session with `useSession(ZerospinOwner)`. It derives the required domain User ID with `User.prefixId(session.browserUserController.userId)`, matching the Clerk User ID installed by `ZerospinOwnerProvider` and the deterministic User ID created during owner authentication.
12. Clicking “Create site” clears any prior inline error and calls `stageCommand` with `contractName: "createSite"` and payload `{ userId }`.
13. The button has no pending state under any circumstance. It is not disabled, its label remains “Create site,” and the page renders no loading text, spinner, or progress indicator while the Promise-shaped staging result resolves.
14. An encoded `Right` navigates immediately to `/site/${result.right.payload.id}`. Navigation does not wait for automatic push, manual DevTools push, or server confirmation. The existing `/site/:siteId` route performs the canonical redirect to `/site/:siteId/page/home`.
15. An encoded `Left` leaves the user on the dashboard and renders its message beside the button in an inline element with `role="alert"`. The unchanged button can be clicked again.
16. Site creation does not stage `createPage` or `createGrid`. The current site workspace renders without querying those records, and its established `home` route remains route state rather than an implicitly created Page resource.
17. The existing Zerospin owner provider remains push-paused. This feature changes neither session configuration nor DevTools behavior.

## Testing Decisions

1. Add `packages/zerospin/src/siteContracts.workerd.spec.ts` as the focused contract seam; do not add web component-test infrastructure.
2. The workerd test stages `createSite` with only a valid owning `userId` and verifies the encoded result is `Right`, its payload contains an autogenerated `sit_` ID, and the optimistic Site row uses that ID with `slug`, `name`, and `description` equal to `null`.
3. The workerd test verifies that omitting `userId` fails payload validation rather than generating or defaulting an owner.
4. The workerd test verifies that the existing owner guard still rejects a validly shaped `userId` that does not belong to the active actor.
5. Run `pnpm nx run @qrk.sh/zerospin:test:workerd`, `pnpm nx run @qrk.sh/zerospin:lint`, `pnpm nx run @qrk.sh/web:typecheck`, and `pnpm nx run @qrk.sh/web:lint`.
6. In the authenticated browser at `/morgs32`, verify the button always reads “Create site” and never becomes disabled or presents a pending indicator.
7. Verify one successful click navigates through `/site/:siteId` to `/site/:siteId/page/home`, where `:siteId` is the ID returned by the staged command.
8. Exercise an encoded staging failure and verify the dashboard remains mounted, exposes the error through `role="alert"`, and leaves the button available for another click.
9. Run `git diff --check` and confirm unrelated work in progress remains unchanged.

## Out of Scope

1. A site-creation form, authored initial metadata, slug generation, duplicate-site prevention, and creation limits are excluded.
2. Creating a default Page, Grid, or Brick is excluded.
3. Waiting for push, server acknowledgement, or authoritative command finalization before navigation is excluded.
4. Loading states, transitions, disabled-button states, spinners, and pending labels for `stageCommand` are excluded.
5. Toast infrastructure, a new component-test harness, and new dashboard abstractions are excluded.
6. Changes to Zerospin session, push-queue, DevTools, or provider behavior are excluded.
7. Cleanup or deletion of persisted local Zerospin state is excluded.

## Further Notes

1. The Zerospin first-party LLM wiki records “no pending UI for local staging” in `llm-wiki/patterns/react/no-pending-ui-for-local-staging.tsx`; implementation should follow that pattern even though `stageCommand` returns a Promise-shaped encoded Either.
2. `session.browserUserController.userId` is the Clerk identity string supplied to `ZerospinConfig`; it is not already a QRK User model ID and must be passed through `User.prefixId`.
3. The generated Site ID is read from the successful staged command payload, not recomputed in the dashboard and not looked up from a persisted table.
