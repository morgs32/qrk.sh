# Offline loading and update prompts for QRK

Researched **2026-10-19** against current primary documentation, upstream source, and QRK's working tree. Scope: load the existing web app while offline and prompt when an updated app is ready. This is research only; no dependency/configuration change or runtime verification was performed.

## Recommendation

**Yes: use a service worker to precache the app shell/resources, with a user-controlled update prompt.** `vite-plugin-pwa` is a candidate for QRK's existing TanStack Start/Vite build. Its `manifest: false` option disables manifest generation while leaving the service worker available; `registerType: 'prompt'` selects the update behavior. Installation, home-screen icons, and a web app manifest are outside the requested scope. [Manifest option](https://vite-pwa-org.netlify.app/guide/service-worker-without-pwa-capabilities), [independent manifest setting](https://github.com/vite-pwa/vite-plugin-pwa/blob/355cf3dd283ca50da3ac4759501e9c3312a3da91/src/options.ts#L98-L112), [prompt behavior](https://vite-pwa-org.netlify.app/guide/prompt-for-update)

The “service worker without PWA capabilities” documentation demonstrates disabling several features together. For this requirement, keep precaching and registration enabled: copying that example's `injectRegister: false` and disabled precache injection would require supplying those behaviors separately. The plugin's generated-worker strategy is the relevant starting point to evaluate. [Minimal-worker example](https://vite-pwa-org.netlify.app/guide/service-worker-without-pwa-capabilities), [generated-worker strategy](https://vite-pwa-org.netlify.app/guide/)

## Expected behavior

1. **Visit online first.** The browser downloads the app, registers the service worker, and downloads the selected resources into its cache. Registration, installation, activation, and control must succeed before relying on offline loading. A first-ever uncached visit cannot work offline. [Worker lifecycle](https://developer.chrome.com/docs/workbox/service-worker-lifecycle/)

2. **Open or reload an app URL offline.** A controlled navigation receives the cached HTML shell; the browser loads cached JS/CSS and other required resources, and TanStack Router resolves the route locally. This needs an explicit navigation fallback and a complete cache for the intended screen. Workbox generates the worker from selected files and configured navigation/runtime rules. [Build and caching](https://developer.chrome.com/docs/workbox/modules/workbox-build), [navigation routing](https://developer.chrome.com/docs/workbox/modules/workbox-routing)

3. **A new release becomes ready while online.** When the browser discovers and installs the changed service worker, Vite PWA exposes `needRefresh`/`onNeedRefresh`. Show a small “Update available” prompt with **Reload** and **Later**. Accepting calls the supplied update function and reloads into the new version; dismissing the UI lets the current page continue. The new worker can also activate naturally after the old worker has no clients, so “Later” defers disruption of this page rather than pinning a version forever. [React update state](https://vite-pwa-org.netlify.app/frameworks/react), [prompt action](https://vite-pwa-org.netlify.app/guide/prompt-for-update), [waiting-worker lifecycle](https://developer.chrome.com/docs/workbox/service-worker-lifecycle/)

The prompt means an update has downloaded and is ready to apply. Deployment alone does not instantly notify every long-open tab: detection follows browser update checks. Detection cadence for a long-lived QRK tab remains a design choice; no periodic/push machinery is proposed here. An offline browser cannot discover a new server release. [Update detection and long-lived sessions](https://developer.chrome.com/docs/workbox/service-worker-lifecycle/#manually-triggering-update-checks)

## QRK fit and concrete constraints

- **The app already has a static shell.** `apps/app` pins Router **1.170.45** and Start **1.169.3**; its Vite configuration enables Start SPA mode and emits `/index.html`. Vite PWA's current generated-worker default fallback is also `index.html`. This makes the approach plausible, but plugin ordering, build output, injection, and offline deep links remain unverified. [Packages](/Users/morgs32/GitHub/qrk.sh/apps/app/package.json:29), [shell configuration](/Users/morgs32/GitHub/qrk.sh/apps/app/vite.config.ts:13), [plugin fallback](https://github.com/vite-pwa/vite-plugin-pwa/blob/355cf3dd283ca50da3ac4759501e9c3312a3da91/src/options.ts#L81-L96)

- **The root URL currently leaves the app.** `apps/app/routes/index.tsx` sends `/` to Web's `/replace`. Returning cached app HTML for `/` would still run that route logic and attempt the Web flow. Offline access therefore needs a usable existing in-app URL or a deliberate change to this redirect. The app's worker cannot control another origin's auth document. [Index route](/Users/morgs32/GitHub/qrk.sh/apps/app/routes/index.tsx), [app/Web ownership](/Users/morgs32/GitHub/qrk.sh/apps/app/AGENTS.md), [worker origin/scope](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register)

- **Include the real runtime resources.** QRK emits a Zerospin SharedWorker and SQLite WASM. Offline boot needs those and whichever fonts/images/modules the intended screen requires; cached HTML alone is insufficient. Audit the actual generated precache and file sizes. Workbox documents a default glob including JS/WASM/CSS/HTML, while Vite PWA's asset docs still omit WASM; the plugin also documents a default **2 MiB per-file limit**. [QRK worker import](/Users/morgs32/GitHub/qrk.sh/apps/app/zerospin/userSession.ts:12), [runtime assets](/Users/morgs32/GitHub/qrk.sh/apps/app/README.md:64), [Workbox defaults](https://developer.chrome.com/docs/workbox/modules/workbox-build#type-GlobPartial), [asset docs](https://vite-pwa-org.netlify.app/guide/static-assets), [size limit](https://vite-pwa-org.netlify.app/guide/faq#missing-assets-from-sw-precache-manifest)

- **Registration must run in the browser.** Start's SPA shell is prerendered using its server build. Vite PWA documents guarded dynamic loading for its registration module in SSR/SSG contexts. [Start shell rendering](https://tanstack.com/start/latest/docs/framework/react/guide/spa-mode), [registration boundary](https://vite-pwa-org.netlify.app/guide/prompt-for-update#ssrssg)

- **Keep reload under the user's control.** The plugin's default `prompt` behavior fits this requirement. Its `autoUpdate` mode can reload open windows with virtual-module registration; the documentation warns about losing in-progress form data. For QRK's editing UI, the prompt should offer a deliberate reload. [Automatic-reload behavior](https://vite-pwa-org.netlify.app/guide/auto-update)

- **Vite+ is already wired.** QRK builds with `vp build` and aliases Vite to `@voidzero-dev/vite-plus-core@1.0.0`. Vite+ documents the standard Vite production pipeline and plugin support. There is no source-supported need to replace that wiring; the exact Start/Vite+/PWA combination still needs verification. [App dependencies](/Users/morgs32/GitHub/qrk.sh/apps/app/package.json), [workspace alias](/Users/morgs32/GitHub/qrk.sh/pnpm-workspace.yaml:5), [Vite+ build](https://www.viteplus.dev/guide/build), [plugin runtime alias](https://www.viteplus.dev/guide/local-cli)

## What offline loading would establish

It would establish that an already cached app can boot at a supported app URL without the network. It would not establish that Clerk authentication can initialize offline, every record is locally available, or commands survive/reconnect correctly. Those are separate behaviors of QRK's existing auth/data/session wiring. [Clerk configuration](/Users/morgs32/GitHub/qrk.sh/apps/app/app/App.tsx:16), [Zerospin session](/Users/morgs32/GitHub/qrk.sh/apps/app/zerospin/userSession.ts), [worker entry](/Users/morgs32/GitHub/qrk.sh/apps/app/zerospin/node.worker.ts)

Keep resource caching separate from command/session ownership. This request does not require introducing a second data cache, an outbox, or background synchronization. Also, cached resources remain subject to browser storage quota/eviction; an online visit once is not a permanent offline guarantee. [Browser storage lifecycle](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## Current tooling evidence

I found no separate official **TanStack PWA** product in TanStack's library catalog. Vite PWA is independently maintained and documents React registration, with no dedicated Start integration listed. TanStack currently labels Start **stable**. [TanStack libraries](https://tanstack.com/), [Vite PWA integrations](https://vite-pwa-org.netlify.app/frameworks/), [Start overview](https://tanstack.com/start/latest/docs/framework/react/overview)

Vite PWA's current GitHub release is **2.0.0** (October 3, 2026); its package declares Node **>=20.19.0**, Vite peers including **8.x**, and Workbox **7.4.1** ranges. Its documentation navigation still displays **v1.2.0**, so selected-release source and generated output should settle exact compatibility/defaults. These are support declarations, not QRK runtime results. [Release](https://github.com/vite-pwa/vite-plugin-pwa/releases/tag/v2.0.0), [release package](https://github.com/vite-pwa/vite-plugin-pwa/blob/v2.0.0/package.json), [published documentation](https://vite-pwa-org.netlify.app/guide/static-assets)

**Unverified here:** production build integration, successful worker control/precache, offline cold reload and deep links, Clerk/Zerospin startup offline, and the old-version → update-prompt → accepted-reload flow. Those are the relevant outcomes for a future implementation.
